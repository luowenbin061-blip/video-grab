两条新需求的可行性报告

① 工具箱：粘贴磁力链接 → 解析 + 播放 + 下载  |  ② 工具箱：粘贴 B站 / 抖音 / 小红书 / 快手链接 → 无水印下载
结论都对着公开资料 + 我们的源码核实过；核不实的地方我单独标出来，没编。

先给结论（四条）

  1. 两条都做得出来，但它俩不是一类东西 —— 一条是「重活，打通一次长期有效」（磁力协议十年没大改）； 另一条是「轻活，但会过期」（平台的接口和签名一直在改，属于长期拉锯）。这个区别比"能不能做"更重要。
  2. 平台解析里，B站最稳：它的签名是纯算法（公开、可移植），而且音视频分离这件事 我们已经有现成的合并能力。抖音 / 快手 / 小红书是"跟平台斗智"，做好了也会隔段时间失效。
  3. 磁力的难点不在"下载"，在两件事：把 BitTorrent 引擎（C++）编进 iOS； 以及「边下边播」—— 现成能用的那个库，连它自己都还没做这个。
  4. 两条需求可以共用一个入口（工具箱加一格「粘贴链接」，自动分辨是磁力还是平台链接）， 比你原计划的"加两格"更干净 —— 也符合你一贯的「一个入口」习惯。

一、需求② 平台无水印下载

先说清一件事：所谓"去水印"根本不是"把水印擦掉"

所有这类工具（包括那些小程序、在线站）用的都是同一条路：调平台自己的数据接口， 从返回的 JSON 里取那条"没叠水印的原始视频流" —— 平台本来就把干净的那条放在接口里， 只是网页版/App 播放时又给你叠了一层水印而已。

所以要干的活只有两件：算出请求签名（证明"这个请求是合法的"）+ 解析返回的 JSON。 另一条路（逐帧 AI 修补水印）需要显卡、还掉画质，我们不做、也没必要做。

逐平台可行性

平台可行性核心活儿凭据风险 / 前提
B站 高 WBI 签名（纯算法：取 key → 固定乱序表重排 → MD5 盖章）
+ 音视频两条流分别下 → 合并		 算法在开源项目（如 DownKyi 的 WbiSign.cs）和多篇技术文里是完整公开的 1080P+ 要登录 Cookie（更高清要大会员）；签名算法平台会更新
抖音 中 a_bogus / msToken 签名（混淆过的 JS 算法）
+ 可能必须带 Cookie		 有"三个端点依次尝试"的成熟做法；老接口对公开作品可能免登录直接返回 签名要么移植、要么塞个 JS 引擎进去算；接口改动最频繁的一档
快手 中 解析接口 + 请求头/设备指纹 有开源实现（KS-Downloader 一类），思路与抖音同 同上；成功率依赖请求头伪装得像不像
小红书 中 链接有四种格式（含 xhslink.com 短链要先展开）
+ 解析页面里的数据 + Cookie		 有开源实现（XHS-Downloader），链接识别做得比较细 不带 Cookie 只给 720P；链接格式平台会改
三个必须提前说清的点
  • "会过期"是这类功能的固有属性，不是我手艺问题。平台一改签名，规则就废 —— 要么接受"隔段时间修一次"，要么接受"失效了就先不用"。
  • 不保证高清。多数平台的"高清直链"要登录态 Cookie。真要做高清，就得在设置里加一项"填 Cookie"（填了才给高清）—— 这一点你拍板。
  • 不碰"擦水印"那条路。逐帧修补要显卡、还掉画质，跟"取原始流"是两回事。
好消息：这件事我们已经有一大半了 现成的：嗅探、下载器（多连接分块）、ffmpeg 合并、HLS 那条线、本机 HTTP 服务 —— 全都在跑。
真正缺的只有"解析器"这一层（算签名 + 解 JSON + 挑出最高画质那条直链）。
而且我们已经有「用户脚本」体系（能导入 JS 脚本）—— 社区里有现成的各家下载脚本。 这条路我没验过能不能跑通（见文末「我不能确认的」），但值得先试一次 —— 如果通，成本能再降一大截。

二、需求① 磁力链接

磁力链接里没有文件，只有一个"编号"

magnet:?xt=urn:btih:... 里那串东西只是文件的指纹（20 字节）。 要拿到真正的文件，必须有完整的 BitTorrent 协议栈：去 DHT 网络找持有这个文件的节点 → 交换元数据 → 分片下载。 在 iOS 上，唯一现实的路径是把 libtorrent（C++ 库）编成静态库搬进来。

现成的 Swift 封装：两个坏消息

现成的库平台要求我们能直接用吗说明
LibTorrent-swift iOS 17 / Swift 6 不能 它的门槛比我们的部署目标（iOS 15，你真机 16.6）高，编不过去
SwiftyTorrent iOS 15+ 能参考 它就是 iOS 上的 BT 客户端，可以扒它的 BT 模块和构建脚本。但它的待办清单里明写着：「边下边播的分片优先级」和「接播放器」都还没做

三个难点（按工作量排）

#难点有多大怎么办
1 把 libtorrent + Boost + OpenSSL 编成 iOS 静态库 一次性、耗时 我们的云编译是 macOS 环境，编得出来；但不该每次构建都编 —— 编一次、产物存进仓库，后面直接复用（我们放 ffmpeg 静态库就是这么干的）
2 边下边播 最麻烦 BT 分片是乱序来的，要"边下边播"就得让引擎优先下你正在看的那一段 —— 这叫分片优先级调度，现成库里没有，得自己写
3 后台 / 锁屏继续下 中等 iOS 会把后台进程挂起。我们已经有"画中画保活"这套经验（下载用它撑过后台），可以搬过来
复用度很高（这条线是通的） 下下来的文件 → 直接用我们已有的本机 HTTP 服务喂给播放器，播放器那一侧不用改。
一个现实提醒（不是技术问题） 磁力能不能下动，取决于有没有人做种：热门资源快，冷门资源基本没速度。国内 DHT 环境和 tracker 状态也会影响。 这不是我们的代码能改的 —— 别到时候以为是我没做好。

三、两条放一起看：我的建议

做哪块投入回报会不会过期我的建议
平台解析 · B站 中 高 会 先做这个 —— 确定性最高，我们现成能力用得最多
平台解析 · 抖音/快手/小红书 中 中 会，且频繁 第二批。做成"一个平台一个规则文件"，失效时只改那一个文件、不用动别的
磁力 大 中（用得上，但不天天用） 不会 单独一轮。而且建议先做"只下载不边播" —— 省掉最难那块，成本差不多能砍一半
我最想让你先知道的一件事（认知差） 你可能会把这两条当成"同一类需求"（都是粘个链接然后下载）。但它们的成本结构和寿命完全不是一回事：
· 磁力：前期很重，打通之后基本一劳永逸（BT 协议十年没大改）；
· 平台解析：前期不重，但它一直在跟你消耗 —— 平台一改就得跟。
如果只按"能不能做"来决定先做哪个，很可能会把最费力的那个排在前面、把最常用的那个拖到最后。

四、需要你拍板的四个点

1. 平台解析先做几个？
我建议 先做 B站 + 抖音（覆盖最常用），跑通"解析 → 下载 → 合并"整条链之后，再把快手/小红书按同一套加进去。
2. 要不要加"填 Cookie"这一项？
不填 = 只有低清；填了 = 高清（B站 1080P+ 还要大会员）。不加这一项，高清基本拿不到。
3. 磁力：先做"只下载"还是直接冲"边下边播"？
先只下载 = 省掉最难那块（分片优先级调度），下完再看（我们播放器直接能放）。
4. 入口怎么放？
我推荐 工具箱加一格「粘贴链接」：粘什么进去都行，自动认（磁力 → BT；平台链接 → 对应解析器）。 比你原本说的"加两格"更干净，也更符合你"一个入口"的习惯。

五、我不能确认的部分（如实标）

这几条我没验过，不许当结论用
  • 抖音那几个接口现在还能不能用、要不要 Cookie —— 必须拿一条真链接实测才知道。动手前我会先做一次只读探测（不改代码）。
  • 小红书 / 快手的具体接口细节 —— 我只查到"有成熟开源实现"，没亲自验当前是否有效。
  • B站 WBI 签名算法是公开的，但"公开"不等于"不会变" —— 平台改了我保证不了。
  • libtorrent 能不能顺利编进我们的云编译 —— 这是整件事里最大的未知数，要真编一次才知道（我倾向先拿它做一个空跑验证，别一上来就写功能）。
  • "用户脚本能不能替代一部分平台解析" —— 我们已有脚本体系，理论上社区脚本能用，但 iOS 的网页沙箱（跨域限制）可能拦它，需要实测。

六、DeepSeek 复核（2026-10-09 追加）

按老规矩把上面这份判断发给了 DeepSeek 复核（只发一家）。它给了三条我原来没有的信息， 其中一条把我的判断改了一半。它说的每一条我都单独核实过，下面分「成立 / 推翻 / 要加前提」列清。

6.1 最关键的一条：磁力引擎的编译，别人已经全踩完了

它指出有一个开源项目 libtorrent_flutter，已经用 GitHub Actions 把 libtorrent 编成了 iOS 的 xcframework， 并且内置了一个本地 HTTP 流媒体服务器来做边下边播。我查了它的更新日志 —— 这条完全成立，而且比它说的更细：

别人已经解决掉的问题对我们意味着什么
CI 里编 libtorrent + 桥接层，xcodebuild -create-xcframework 打包，只出 arm64-iphoneos 一个切片 我们真机是 arm64、TrollStore 侧载不用签名 → 连模拟器切片都不用编，比它还省
SystemConfiguration.framework 必须显式链接（不加，iOS release 链接直接报 Undefined symbol: _SCNetworkReachabilityCreateWithAddress） 这是那种能耗掉一整天的坑，现在写在纸上
OpenSSL 要静态编、且每个切片单独编一次（3.2.1）依赖清单确定，不用试
MSE/PE 加密必须开 —— 之前 iOS 版是关的，导致很多 seedbox 拒绝明文连接，实际可连的 peer 少一大截 直接决定"下得动不动"，这条不说我会踩
但有两条它没说，我必须补上（很重要）
  • 授权不一样，别抄代码。libtorrent 本体是 BSD-3-Clause（宽松，自用无约束 —— 它这条说对了）； 可 libtorrent_flutter 这个封装项目是 GPL v3（它 1.2.0 起从别的协议换过去的）。 GPL v3 有传染性 → 它的桥接层代码、流媒体服务器代码，一个字都不能抄进我们的项目。 能用的是"它踩过的坑"这个信息（要链哪些 framework、怎么切切片），不是它的代码。
  • 它把"边下边播"说成"以后再补一层" —— 从更新日志看，那一层（头 5 个 piece + 尾部 512KB 预取、 动态预读窗口、seek 时清掉旧分片优先级、LRU 分片缓存）占了那个项目更新日志的绝大部分篇幅。 也就是说：那一层才是真正的大头，不是"顺手加一下"。它建议先砍掉，我同意，但理由要记对。

6.2 它的第二条：抖音/小红书/快手 别自己算签名，用网页自己算

它提了一条我原报告里没有、而我们恰好最有条件做的路子 —— 不碰签名，改成"让网页自己去请求"：把分享链接用我们的浏览器打开 → 页面里的 JS 会自己带上正确签名和 Cookie 去要视频 → 我们早就有的嗅探器直接把真实地址接住 → 交给下载中心。

为什么这条对我们特别便宜
  • 我们这个 App 本身就是一个浏览器，嗅探器、本机代理（补齐 Referer/UA/Cookie）、下载中心全是现成的。
  • 这条路一行签名算法都不用写 —— 而签名（抖音的 a_bogus、小红书的 x-s）恰恰是"写一次、隔几天失效要重写"的那部分。
  • 它给的具体判断：抖音的 a_bogus 是虚拟机保护的 JS（要过国密 SM3、逐字节异或混淆）， 而且有开发者报告"同一套代码几小时后批量失效"（平台按批次热更）。这一条我没核实，但它据此建议"别碰抖音"。
这条路我还没验证的地方（不许当结论）
  • 这些平台的网页版可能强制跳 App / 要求登录，那样网页里就没有视频可嗅。
  • 就算嗅到了，拿到的可能还是带水印的那一条（真正的无水印流要走它们的内网接口才有）—— 这一条必须拿真链接实测才知道，我倾向先拿快手的分享页试。
  • 平台可能识别我们的浏览器不是标准 Safari 而给降级页面。

6.4 它和我分歧的地方（只有一处）

先做哪两个理由
我原报告的排法
B站 + 抖音		 按「你最常用」排 —— 抖音覆盖面最大。
它的排法
B站 + 快手		 按「最快见到能用」排 —— 快手有成熟开源实现、分享页简单；抖音投入产出比最差。
两种排法目标不同，都不算错，得你定

要「先把一条链跑通、看得见结果」→ 选 B站 + 快手； 要「一步到位覆盖最常用的」→ 选 B站 + 抖音，但抖音可能白做（签名很容易失效）。 我个人偏向前者：先跑通流程，比先赌最难的那家稳。
