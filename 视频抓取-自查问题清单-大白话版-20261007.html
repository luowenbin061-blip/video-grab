VideoGrab 自查问题清单 · 大白话版

对象：当前最新版 v1.0.235（真机 iOS 16.6）· 这次是我自己读代码查的（不是再问 AI）· 每条都在代码里指到了具体位置 · 2026-10-07 深夜

先说结论

查到 11 个真问题。其中最要紧的是 3 个：

  • 「备份」其实少备了三样东西，还骗你说成功了 —— 换机重装后标签页、视频历史、首页快捷格子全没了。
  • 暂停/取消下载后，有个每秒响一次的闹钟忘了关，还一直拽着那个任务不放 —— 用得越多越费电、越卡。
  • 本机播放服务会"假死" —— 一边下一边播的时候容易堆住，而且它自己查不出来，只能重启 App。

标注 本轮新发现 的两条，是之前问 AI 时没有任何一家提到的（因为它们没看到这部分代码）。

一、会让你「丢东西」的

最要紧1. 备份少备三样，却提示「已恢复成功」本轮新发现

你看到的：设置里点「导出备份」→ 换手机 / 重装 → 点「恢复」→ 它说 「已恢复 3 个数据文件、N 项设置」。你以为万无一失。
实际情况：你的标签页、视频历史、首页那几个快捷格子——一样都没备进去。真丢了你也不知道，因为它不会报错。

为什么：它拿着一张"要打包哪些文件"的单子去下载目录里找，但单子上写的位置和东西实际放的位置不是一个地方：

它去找东西实际在结果
根目录下的 tabs.jsonTabs/tabs.json（多一层文件夹）找不到 → 静默跳过
根目录下的 shortcuts.jsonhome/shortcuts.json找不到 → 静默跳过
单子上压根没写视频历史watch_history.json从来不备

证据：DataBackup.swift:26（单子）与 :82（try? … else { continue } 读不到就跳过，不报错）； TabStore.swift:155、HomeShortcuts.swift:97（真实路径）。

修起来：小改 —— 把单子上的路径改对、把视频历史加进去、读不到就明确告诉你「这几样没备上」。

二、会让 App「越用越沉」的

要紧2. 暂停 / 取消下载后，有个"每秒响一次的闹钟"忘了关本轮新发现

你看到的：下过一堆东西、又暂停/取消/删掉了很多任务之后，App 开始费电、发热、变卡，内存也回不去。
实际情况：App 里有个「每秒醒一次、看看内存用了多少」的小闹钟（用来记录"下载时内存峰值"）。 它只在任务正常跑完时才会被关掉；你要是**中途暂停或取消**，它就一直响下去—— 而且它还牢牢抓着那个任务不放，等于那个任务也永远删不干净。

为什么：管"关闹钟"的那句代码，只在一个地方被调用（"某个阶段正常结束"时）； 而"暂停""取消"这两条路都没叫它。这个任务类也没有"自我清理"的收尾动作。

证据：DownloadJob.swift:134-148（闹钟里 let target = self 强引用自己）、 :120-121（只有阶段结束才关）、:338（暂停不管）、:376（取消不管）、以及这个类没有 deinit。

修起来：很小 —— 暂停和取消时各补一句"关闹钟"。属于"改两行，省很多电"。

中等3. 图片列表没有上限，「清空列表」还清不掉它

你看到的：逛图多的站（图库、瀑布流）之后，内存涨上去下不来； 更怪的是——你点了「清空列表」，回头再进图片那一栏，老图又自己冒出来了。

为什么：视频列表有「最多 500 条」的保护，图片列表没有。 而"清空"这个动作漏清了一样东西——每个标签自己私藏的那份图片备份。 下次页面一上报，它就把这份私藏又合并回来。

证据：BrowserModel.swift:1939-1941（视频有截断）vs :1956（图片直接赋值，无截断）； :1660-1666（清空时只清标签里的"视频/分组"，没清它的"图片/图片分组"）。

中等4. 好几个"记事本"只往里写、从不往外撕

你看到的：用得越久，内存慢慢往上涨（不剧烈，但一直在涨）。
实际情况：有四五样东西是"只增不减"的：清晰度候选、画中画状态、每个任务的详细日志、缩略图重试记录、 以及播放代理里那张"每个视频的请求头"表。

为什么：这些都用「以地址为键的字典」存，用完没人删。 其中播放代理那张表还存着 Cookie/Referer，会一直留在内存里。

证据：BrowserModel.swift:2044-2050（4 个字典）、DownloadJob.swift 的 notes 只 append、MediaProxy.swift:47-53（静态表无上限无超时）。

三、会让「播放 / 网页卡住」的

要紧5. 本机播放服务会"假死"——堆住了自己也查不出来

你看到的：一边下东西一边播（尤其"同时下载数"设成不限），播着播着就转圈/播不出来； 更糟的是之后所有视频都播不了，只能把 App 杀掉重开。
实际情况：App 里有个自己写的"小服务器"，播放视频时所有数据都要从它这儿过。 它来一条请求就开工一条、不设上限，而且每一条都可能干等上游 35 秒（连着失败重试的话，一条能等上百秒）。 请求一多，工位全被占满 → 新来的只能排队 → 就是"卡住"。

更要命的是第二半：这个服务器有个"体检"动作，但它只是敲一下门、听有没有人应声， 并不问一句"你还能干活吗"。所以它明明已经卡死了，体检报告还是"健康" → 系统不去重启它 → 永远好不了。

证据：LocalHTTPServer.swift:40（并发队列不设上限）、:372（每连接一个任务）、 MediaProxy.swift:324-332（同步等 35 秒）、LocalHTTPServer.swift:132-151（体检只做 TCP 连接）。

修起来：中等 —— 给工位设个上限（比如最多同时 16 条）+ 把体检改成"真的发一句 HTTP 问话"。

要紧6. 同一个视频"刷新地址"只会做一次，刷新完再失效就不管了

你看到的：看长时间的视频，播到一半突然播不动，退出去重进又能播一会儿。
实际情况：这类站的视频地址是短命的（几分钟就作废）。App 发现地址失效会"回原页面重新问一遍"， 但只肯问一次——第二次失效它就直接放弃，把 403 错误甩给播放器，得干等 5 分钟才肯再问。

为什么：判断"要不要重新问一遍"的那句话里，多了一个条件： "必须是原始地址才重新问"。可第二次用的是上次问回来的新地址，条件不成立，就跳过了。

证据：MediaProxy.swift:225-231（那句 effective.absoluteString == up.absoluteString）、 :87-92（新地址缓存 5 分钟）。

修起来：小改 —— 把条件从"必须是原始地址"改成"这一跳还没重试过"。

中等7. 上报视频清单时「先记账、后发货」

你看到的：偶尔碰到某个页面：左上角的「窗口」按钮就是不出来，视频历史里也没有这一页 —— 而且刷新一下又好了。
实际情况：页面把"这页有哪些视频"报给 App 时，是先把"我已经报过了"记在本子上，再去送信。 万一那次送信失败（页面太复杂、一次要送的太多），本子上已经记成"报过了" → 只要视频没变化，它就再也不会重发。

证据：sniffer.js:641-653（vidSig = sig; 在 postMessage 之前，且发送被 try{}catch{} 吞掉）。

修起来：很小 —— 把"记账"挪到送信成功之后。

四、特定操作下会出的错

中等8. 暂停后马上点继续，状态可能显示反

你看到的：点了暂停、马上点继续，结果界面上写着"已暂停"，可它其实在下 —— 或者反过来，重启后还是错的。

为什么：老的下载任务还没停干净，新的就已经开工了；老的那个收尾时"把'暂停'的牌子又立了回去"， 把新的状态盖掉了。

证据：DownloadJob.swift:338-345（暂停立刻松手）、:359-374（继续只检查"手空了没"）、:1059-1065（旧任务收尾时又置 paused = true）。

中等9. 导入视频失败时，界面一声不吭

你看到的：从相册/文件里选了个视频，点确定 —— 什么都没发生。
实际情况：失败的原因（iCloud 还没下载完、文件被系统回收、空间不够）被悄悄咽掉了， 也没有"一条都没导进来"的提示。

证据：Importer.swift:40-42（catch 里只有一句注释）、ContentView.swift:61（空的就默默返回）。

中等10. 几个"存档"读坏了就当空的，然后一次写回把旧的覆盖没

你看到的：某次之后，压缩队列空了 / 续看进度全没了 / 首页快捷格子不见了，而且再也回不来。
实际情况：这些存档如果读到一半坏了（比如上次被系统杀掉、文件写了一半），代码不报错、当空的处理； 接着任何一次保存动作，就用"空的"把原来那份盖掉了 —— 数据彻底没了。

证据：CompressQueue.swift:465-467、WatchProgress.swift:69-73、HomeShortcuts.swift:231-232（都是 else { return [] } 之后无条件写回）。

轻微11. 几处小毛病（知道就行）

  • 播放器「重试」是原样重来：不换地址、不重置"已经兜底过一次"的标记，失败后点重试可能又是同一条坏地址，然后又要转 60 秒圈。
  • 画中画"开机梯子"关不干净：正在启动画中画的那几秒里你把它关了，它过一会儿可能自己又冒出来。
  • 任务记录写盘失败不吭声：磁盘满导致记录没写进去，重启后下载列表"凭空清空"，全程无提示。
  • 标签休眠时只摘了三个消息通道里的一个（另外两个没摘）—— 影响很小，但属于没做干净。

五、如果只修三件事，我先修这三件

优先级修什么为什么先修它工作量
1 备份路径改对（+ 加进视频历史 + 读不到要报错） 这是唯一一条会真丢你的数据，而且你现在还以为它好使 小
2 暂停/取消时关掉那个"每秒闹钟" 两行代码，直接解决"越用越费电、越用越卡" 很小

其余 8 条（并发上限、图片列表上限、字典清理、暂停竞态、导入提示…）可以排后面， 它们要么影响慢、要么只在特定操作下出现，不急。
