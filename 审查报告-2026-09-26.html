一、今天的总结

今天从 v1.0.58 走到 v1.0.83，四条线：

① 长按下载（v1.0.58 → v1.0.62）—— 推倒重做

版本做了什么
v1.0.58试「网页层盖透明链接、借 Safari 系统菜单」→ 实测失败
v1.0.60推倒重做：改成「原生长按手势 + 自绘菜单」；加长按诊断开关
v1.0.61修「大多数页面不弹」：命中测试加几何兜底 + 修兜底竞态
v1.0.62拆掉「长按自动弹嗅探面板」（用户明确不要）

为什么 v1.0.58 那条不通：WebKit 在手指按下瞬间就锁死长按目标；系统菜单回调只对链接/图片触发；Safari 那套带预览卡的菜单是 WebKit 私有逻辑，只给 Safari 和它的扩展。

这段的教训（已写进技能）：
  • 你说「偏大」我缩到 18pt —— 量完截图才知道 21pt 才对，白走一轮。主观描述只能定方向，数值必须量。
  • 系统控件占哪些位置（左上 ✕/画中画、右上音量、底部进度+右下水印）→ 自定义按钮只能放空位。
  • 「要点两三次」不是手感，是两个按钮撞在一起抢点击。
  • 已经决定跟随系统，就别再把同一件事在本地实现一遍（乐观切换 → 交替点播放/暂停时图标反复显隐）。
  • 「慢」的真身是节奏不是延迟：系统控制条是渐变的，我们做成「啪」地切换 → 时刻对得上但一眼看出不是一路的。

顺带解决的两件事

  • 下载通道：你的代理到期 → GitHub 直连不通、内置代理只有 6.4 KB/s。实测 8 个国内镜像，只有 gh-proxy.com 可用（128 KB/s，10MB 用 70~83 秒）。每次都用 GitHub 官方 sha256 校验一致才收。
  • 你放弃的那些（我不再提）：网页翻译 · 下拉刷新 · 跨域 iframe 长按 · 播放器自带长按冲突 · 后台下载 · 裁边铺满。

三、★ 核实后成立的 14 条（按优先级）

下表每一条我都对着真实源码核过，附了文件与行号。带「多源」的是多家独立提到、可信度更高。

P0 / P1 —— 值得尽快修

#问题来源优先级证据 / 说明
1 m3u8 里的 #EXT-X-MAP 没处理 —— fMP4/CMAF 格式的 HLS 会下出播不了的坏文件 MiMo P0 M3U8.swift 只认 STREAM-INF / KEY / MEDIA-SEQUENCE / EXTINF / DISCONTINUITY， 其余 # 标签一律 continue 忽略（源码原话）。所以 #EXT-X-MAP:URI="init.mp4"（初始化段）和 #EXT-X-BYTERANGE 都丢了。 后果：下到的是一个没有 moov 头的碎片流 —— 看着「下载成功」，实际播不了。
2 标签唤醒的「2 秒保护」会让同时活着的网页超过 3 个 多源 3 家 P1 BrowserModel.swift:539 的 trimLive()： 
while tabs.filter({ $0.isAwake }).count > TabLimits.maxLive {
    let candidates = tabs.filter {
        $0.isAwake && $0 !== cur && now.timeIntervalSince($0.lastActiveAt) > 2
    }
    guard let oldest = candidates.min(...) else { break }   // ← 候选为空就放弃
    sleep(oldest)
}
快速连点切标签时，所有「非当前」标签都在 2 秒内 → 候选为空 → break → 活着的一直堆。 原注释认为「下次切换会补上」，但连续快速切换期间会真实堆到 5~8 个 WebView，每个几十 MB。
3 嗅探结果 items 只去重、没有上限 —— 短视频无限流会一直涨 多源 2 家 P1 BrowserModel.swift:1077 ingest()：var merged: [String: SniffItem] = [:]; for old in t.items { merged[old.url] = old } 然后 t.items = sorted（:1131）—— 旧条目永不过期，只按 URL 去重。 在抖音式无限流上，每滑一个视频就多一个永不消失的 URL → 越用越占内存（也拖累每次上报的排序与界面刷新）。 去重是做过的（两家 AI 都说没去重，这点它们错了），缺的只是上限。
4 音频会话没监听中断 / 路由变化 —— 来电后不自动续播、拔耳机可能外放 MiniMax P1 AudioSession.swift 全文 58 行，只有 acquire() / release() / describe() —— 没有一处 interruptionNotification 或 routeChangeNotification。 这是个视频 App 的核心体验项，属于「用户会立刻卸载」级别。
5 网页进程崩溃后自动重载，没有防「无限重启」 MiMo P1 BrowserModel.swift:1290 webViewWebContentProcessDidTerminate 里直接 wv.reload()，没有计数。 碰上「一加载就把渲染进程搞崩」的页面 → 崩 → 重载 → 崩，无限循环，风扇起飞。
6 画中画被用户手动关掉时，什么都不告诉用户 MiMo P1 PiPProgress.swift:493 pictureInPictureControllerDidStopPictureInPicture 只做了 timer?.invalidate() + releaseAudio()。 而下载的「后台活着」正是靠这个画中画撑着 —— 用户划掉小窗 = 后台执行没了，下载会停，界面上没有任何提示。
7 标签存档解码失败 = 静默全丢，且不给任何提示（升级/字段变动/文件损坏都会触发） DeepSeek P1 TabStore.swift load()：return try? dec.decode(TabStorePayload.self, from: d) —— 任何解码失败都返回 nil，上层当成「没有存档」，用户标签全没且不知道为什么。 TabGroup / TabRecord 都是合成的 Codable，没有 decodeIfPresent 兜底 —— 以后再加任何一个字段，所有老用户的标签就会一次性全丢。

P2 —— 值得顺手做

#问题来源优先级证据 / 说明
8 没设 performance.setResourceTimingBufferSize —— 资源条目默认只留 250 条 MiMoP2 sniffer.js:288 只用 PerformanceObserver，没调过 setResourceTimingBufferSize。 重页面上早期条目会被挤掉（而早期那几条往往正好是真视频地址）。一行代码的量，收益明确。
9 缩略图存成 PNG —— 网页截图是连续色调，PNG 效率极差的 MiniMaxP2 TabStore.swift saveThumb()：guard let d = img.pngData()。 15 张约 7.5 MB → 改 JPEG(0.7) 约 1 MB。顺手把文件名后缀从 .png 改 .jpg 并加一次性迁移。
10 KVO 回调用 Task { @MainActor } 包装 —— 加载期每秒造几十个 Task MiniMaxP2 BrowserModel.swift:494 makeObservations 三个 KVO 都包了 Task { @MainActor in ... }； estimatedProgress 加载期每秒能触发 30+ 次。DispatchQueue.main.async 更轻。
11 长按诊断把「同源 iframe 还没加载完」误报成「跨域」 MiniMaxP2 sniffer.js hitIn：cross: !inner —— contentDocument 对「跨域」和「同源但没加载完」都返回 null，两者无法区分。 不影响功能，但会误导排查（照着「跨域」两个字去改是白改）。
12 唤醒标签时 URL(string:) 失败 → 白屏且无提示 MiMoP2 BrowserModel.swift:485：} else if let u = URL(string: t.address) { wv.load(...) } —— 没有 else。 地址栏手输含中文/空格时 URL(string:) 会返回 nil → 建了 WebView 但什么都没加载，看着就是白屏死掉。
13 重活（整页 HTML 序列化 + 正则）没有时间保护 MiMoP2 60ms 自保只管「轻活」（sniffer.js:269）。重活虽然只在加载完成时跑一次，但超长页序列化 + 正则仍可能卡住主线程数秒。
14 缩略图截图失败没有占位图；私有读法缺「连续失败熔断」 豆包P2 两条都归入「打磨」：① snapshotCurrent() 失败时网格里就是空白卡片；② 读系统控制条已有「两种读数都见过才采信」的有效性闸，但没有连续失败 N 次后停用的熔断。

四、核实后推翻的 15 条（AI 说错了）

这些不用改 —— 我逐条查了源码，实现早就在了。列出来是为了让你知道「AI 的意见不能直接照做」。

#AI 的说法来源核实结论（附证据）
1删标签时没清 TabGroup.tabIDs，组里会留死 idDeepSeek 已有 BrowserModel.swift:707 removeFromGroups(_:) 正是干这个的（清 tabIDs + 清 currentTabID），closeTab 里已调用。

5LocalHTTPServer 要防目录遍历，别把手机文件全暴露DeepSeek 已防 LocalHTTPServer.swift:392 有完整防护：standardizedFileURL + guard target.path == rootPath || hasPrefix(rootPath + "/") → 否则 403。

9嗅探结果按 URL 没去重，同一资源刷好几屏MiniMax 已去重 sniffer.js:52 add()：var key = url.split('#')[0]; if (found[key]) { ...更新 last/hits...; return; }。
10byWebView 字典没清，休眠后残留 → 内存泄漏豆包 已清 BrowserModel.swift sleep() 里就有 byWebView[ObjectIdentifier(wv)] = nil。
11performance.getEntriesByType('resource') 跨域拿不到完整 url，会漏抓豆包 事实错误 Resource Timing 的 name 字段就是完整 URL（只是跨域时拿不到细粒度耗时）。这条是编的。

五、我的判断与建议顺序

如果要动手，我建议先修这 3 条（都在 P0/P1 里，而且互相独立、改动小）：
  1. #1 #EXT-X-MAP —— 这是唯一会「产出坏文件却显示下载成功」的一条，性质最恶劣，而且你迟早会碰到 fMP4 的站。
  2. #7 标签存档解码兜底 —— 现在只是「以后加字段才炸」，趁只有你一个人用的时候改掉成本最低。
  3. #2 trimLive 的 2 秒保护 —— 快速切标签时真实吃内存，改了立刻见效（缩略图那次改为「先截、截完再睡」）。

一条重要提醒：这轮 AI 的意见里，「AI 说这里有问题」和「这里真的有问题」是两件事 —— 30 条里 15 条是错的，比例一半。 错的那些有个共同特征：它们只看我给的那几段源码，就推断「没实现」（其实实现就在没给的文件里）。 所以以后这类外部审查，逐条核实这一步不能省。这条我已经写进技能。

关于几个「AI 说对了但我早说过」的： DRM 不支持、跨域 iframe 长按认不出、PiP 保活的脆弱性 —— 前两条是已列明的取舍（AI 基本守住了没提）； PiP 那条（MiniMax #6）确实是方向性风险：用画中画承载「非视频内容」属于逆向用法，iOS 大版本收紧准入就可能失效。但你现在没有更好的替代（后台下载已放弃），所以我只标注风险、不建议现在改 —— 建议加一条「PiP 启动失败就自动降级」的埋点。
