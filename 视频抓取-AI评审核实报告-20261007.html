VideoGrab 代码评审 · 逐条核实报告

主评审：DeepSeek（另两家部分产出作交叉验证）· 版本 v1.0.235（ipa 11.7 MB / app/ 27351 行 Swift + 注入 JS）· 评审材料：项目简报（含核心代码片段，非全量源码）· 核实时间 2026-10-07 晚 · 所有结论都对过源码，附文件与机制

一句话结论

共识别出 16 条真问题（其中 2 条 P0，都是"播放会中途挂掉且不自愈"这类）， 另有 15 条被推翻 —— 它们说的那些"没做"，源码里其实都做了。

最值钱的一条是两家独立命中同一条：freshAddress 命中刷新后的地址后， 若那个地址也过期，代码会永久跳过刷新（一行布尔条件写错）， 表现就是"播着播着突然 403，再也回不来"。这条以前从没意识到。

二、成立的问题（按危险程度排）

每条都标注了：谁提的 · 依据（文件与机制）· 触发条件 · 怎么修。

P01. 端口漂移之后，已经发出去的代理地址全部作废

提出者：DeepSeek、豆包、MiMo 三家独立命中

依据： MediaProxy.proxyString 把端口写死在 URL 里 （http://127.0.0.1:<port>/__vgproxy/…）； 而 LocalHTTPServer.start() 在普通模式下端口尝试顺序是 [0, 18080, 18081…] —— 首选 0，也就是让系统随机分配。 ensureAlive() 一旦判定服务坏了，会 closeListener() + start()， 很可能绑到另一个随机端口。

触发：播放 HLS 期间本机服务被判定为坏 → 重开 → 换端口。

后果：AVPlayer 手里那份清单里的每一行都是旧端口地址， 后续所有分片/钥匙请求全部 connection refused。 PlayTarget.fallback 是在创建播放器那一刻决定的快照， 播放中途端口变了它不会切换 —— 必须用户手动重新点播放。 （这正是你之前实测到的 -1004 无法连接服务器 的成因。）

修法： ① 普通模式也优先固定端口（18080 起），只在被占用时才退到随机； ② 记录"当前端口代次"，端口变化时通知正在播放的 PlayerBox 重新取地址； ③ 更好但改动更大：让代理地址不带端口 —— 做不到，端口是必须的，所以回到 ①②。

P02. 刷新过的地址再失效，就永远不再刷新（一行条件写错）

提出者：三家独立命中（DeepSeek / 豆包 / MiMo）

依据：MediaProxy.handle 里的刷新分支条件是

if let code = got.resp?.statusCode, code == 401 || code == 403,
   effective.absoluteString == up.absoluteString,  // ★ 只有"用的是原地址"才刷新
   let fresh = refresh(parent: key, up: up) { … }

而 freshAddress() 有 300 秒 TTL。于是：

  • 第一次 403 → 用的是原地址 → 触发刷新 → 把新地址记进 refreshed；
  • 接下来同一个分片再请求 → effective = 刷新后的地址（≠ 原地址）；
  • 这个地址若也 403 → 条件不成立 → 跳过刷新 → 直接把 403 甩给播放器；
  • 要等满 5 分钟缓存过期，才会重新走一次刷新。

触发：站点签发的分片地址有效期短于 5 分钟（实测这类站确实短）。

修法：把条件从"必须是原地址"改成 "403 且这一跳还没重试过"（给 refreshed 地址也允许再刷新一次，并加次数上限避免死循环）。

P13. 自检只做 TCP 连接 —— 会误判"服务还活着"

提出者：DeepSeek、豆包、MiMo

依据：ensureAlive() 的健康检查是 canReachSelf()，它只做一次 TCP connect，不看 HTTP 响应。 TCP 握手由内核完成 —— 哪怕 accept 循环卡死、serve 线程全被占住、HTTP 层完全不响应， connect() 照样成功。

后果：自检说"健康" → 不重开 → 播放持续失败且永不自愈（只能重启 App）。

修法：改成发一个真实 HTTP 请求（例如 GET /__vghealth）并校验响应； 或记录"最近一次成功处理请求的时间"，超时即视为不健康。

附：MiMo 说这还会"消耗 accept backlog 引发重启风暴" —— 这条不成立（见推翻表第 14 条）。

P14. 刷新时只按「路径」找同一行 —— CDN 换域名就配错

提出者：DeepSeek、豆包、MiMo

依据：refresh() 里 candidates.first(where: { $0.path == want })， 只比 path，不看 host、不看 query；refreshed 的键也是 key + "|" + path。同一份清单里若同时存在 cdn1/xx/seg.ts 与 cdn2/xx/seg.ts（路径完全相同、域名不同），就会命中错的那条。

触发：站点在清单里列了多 CDN 镜像，或刷新后整条路径变了。

修法：匹配时把 host 也纳入比较；路径变化时退回"整份清单重新取一次并按顺序对位"。

P15. data: 内联密钥会被错误改写成代理地址

提出者：MiMo（提到规则）· 我核实后确认代码确实如此

依据：rewritePlaylist 把每个 URI 交给 proxyString(for:)，而它没有 scheme 校验 （校验只在 wrap() 里有，handle() 里也没有）。 HLS 规范允许密钥写成 URI="data:…;base64,…"。

后果：内联密钥被换成 http://127.0.0.1…?u=data%3A… → 本机服务取不到 → 解密失败、黑屏。

修法：在 proxyString 加 scheme 白名单（只代理 http/https）， 其余原样返回。一行的事。

P16. 本机服务是「无上限并发 + 每连接同步阻塞最多 35 秒」

提出者：DeepSeek、豆包（豆包列为它心目中的第一优先）

依据：queue 是 DispatchQueue(attributes: .concurrent)（不设闸门），每个连接 queue.async { serve }， 而 serve 里的 MediaProxy.fetch 用 sem.wait(timeout: .now() + 35) 同步阻塞。

触发：HLS 一个清单几十上百个分片并发请求 ＋ 局域网共享 ＋ 下载并发设"不限"。

后果：阻塞任务占满线程池与 fd，新连接排队；播放卡顿、超时。

修法：给 serve 加并发闸门（信号量 16~32 条），超出的排队而不是无限开。

P17. 播放代理与下载共用同一个 URLSession

提出者：MiMo（只有它提到）

依据：MediaProxy.fetch 用 URLSession.shared， 而 Downloader 的分片下载、WatchHistory 的封面下载、 ThumbLoader 也都用 URLSession.shared。 URLSession.shared 对同一 host 的并发连接默认只有 6 条。

后果：一边下载一边播放同一个站时，播放的分片请求要跟下载抢那 6 个槽位， 排队 → 卡顿/超时。并发下载设"不限"时最明显。

修法：给播放代理单独建一个 URLSession（自己的连接池），与下载分开。

P28. 代理的静态表永不清理

提出者：DeepSeek、豆包

依据：table（请求头）与 playlists（父清单地址） 没有上限、没有 TTL；只有 refreshed 有 300 秒 TTL。 注意：写入是加锁的、读取也加了锁（所以"并发字典崩溃"那条不成立）。

后果：长时间使用内存持续增长，且 Cookie/Referer 一直留在内存里。

修法：给两张表加容量上限（如 64 条）+ LRU 淘汰；或按时长清理。

P29. 分片是「整块读进内存再转发」

提出者：DeepSeek、豆包

依据：MediaProxy.fetch 用 dataTask 收完整 body， 塞进 Reply.body（全量 Data）再一次性写 socket。

后果：高码率视频 + 多分片并发时内存冲高（iOS 会先给内存警告，严重则被杀）。

修法：改成流式转发（边读边写）。改动较大，可以排在后面。

P210. acceptLoop 无锁读 running / listenGen

提出者：DeepSeek、豆包、MiMo

依据：这两个变量在锁内写，但 accept 循环里无锁读。

后果：形式上是数据竞争；实际有 myGen != listenGen 的二次校验兜底， 最坏是"旧循环多转一圈"，风险低（不是"必崩"）。

修法：读也走同一把锁，或换成原子量。

P211. 代理路由用的是「子串查找」而不是「前缀判断」

提出者：DeepSeek

依据：rawPath.range(of: prefix) —— 只要路径中间出现 __vgproxy/ 也会命中。

后果：极罕见（要有站点文件名恰好含这段），但确实是逻辑不严。

修法：改成判断前缀位置（hasPrefix("/" + prefix) 或校验 index）。

P212. 清单开头若有 BOM / 空白，可能被当成"不是清单"

提出者：MiMo

依据：识别清单的两个条件是 data.starts(with: [0x23,0x45,0x58,0x54])（即 #EXT）或 Content-Type 含 mpegurl。带 BOM 的清单两边都不满足。

后果：低概率（多数站 CT 正确），一旦发生会把清单当分片转发 → 播放失败。

修法：改成"解码成文本后 trim 再判断是否以 #EXTM3U 开头"。

P213. 上游 200 + HTML 错误页，会被当成分片转发

提出者：三家都提（一致）

依据：非清单分支不校验内容类型， text/html 会被原样带上 Content-Type 发给播放器。

后果：AVPlayer 拿 HTML 当媒体解码 → 报一个看不懂的解码错误（ 你之前截图那类"播放器起不来"的一部分可能就是它）。

修法：内容类型是 text/html、或 body 以 < 开头 → 直接返回 502 + 一句人话。

P214. 视频历史：地址去掉 query 会误合并；时长折半分桶也会误合并

提出者：DeepSeek

依据：videoKey 把 ? 之后全部丢掉 → /play?url=A 与 /play?url=B 变成同一条； mergeKey 用 String(dur / 2) → 时长 100 与 101 落进同一个桶。

后果：这两种都是你已知并接受的取舍（"宁可留一条重复，也不误并"）， 但 DeepSeek 给出的触发场景（聚合站用 query 传真实地址）值得知道。

修法：若要更准：去 query 时只剔掉已知的签名参数（token/t/sign），保留其余； 合并时再加一条"分辨率必须一致"。

P215. 没有监听网络变化（Wi-Fi ↔ 蜂窝）

提出者：豆包（只有它提到）

依据：全项目没有 NWPathMonitor 之类的监听（已 grep 确认）。

后果：切网后 refreshed 里缓存的地址可能整批失效，却仍被优先使用； 上游请求会在旧网络栈上耗到超时。

修法：加一个网络变化监听，变化时清空 refreshed（很便宜）。

P216. 标签休眠时只摘了三个消息通道中的一个

提出者：MiMo 提到"handler 强引用"，我核实后发现真问题在别处

依据：建 WebView 时注册了三个 （vgSniff / vgClean / vgVideos）， 但 sleep() 里只 remove 了 vgSniff。

后果：影响很小（真正的环靠 t.webView = nil 断开， 而 BrowserModel 本来就是 App 级对象不该释放），属于代码不一致，不是泄漏。

修法：三处一起摘，保持对称（顺手的事）。

三、被推翻的结论（AI 说有、核实后不成立）

这一节的用处和上一节一样大：它们说的"这儿没做"，源码里其实都做了。 原因也一致 —— 它们在只看到片段的情况下，按"通用最佳实践"推断"这里大概没处理"。

AI 的主张核实结果证据
MediaProxy 读静态字典没加锁 → 并发崩溃 推翻 headers() / freshAddress() / rememberFresh() 全部 lock.lock()；简报里为了精简只贴了 register 的加锁
NSLock 非递归，可能自锁死 推翻 没有任何"持锁时再进 register"的路径；豆包也独立排除了死锁（"无跨锁依赖，不会死锁"）
refreshed 没有过期检查 推翻 freshAddress 里 Date().timeIntervalSince(hit.at) < 300；写入时还会顺手清过期项
只改写非 # 行 → #EXT-X-KEY/MAP 的 URI 漏改 推翻 rewriteURIAttrs 的判据是"这一行里含 URI=""，与标签名无关 → KEY / MAP / MEDIA / I-FRAME-STREAM-INF / PART 全覆盖
相对路径是手写拼接，遇到 ../、//host 会错 推翻 URL(string: line, relativeTo: baseURL)?.absoluteURL —— 标准解析
HEAD 未处理 / Content-Length 不对 / 416 不合法 推翻 if isHead { return }（不发 body）；Content-Length: body.count；文件路径的 416 带 Content-Range: bytes */总长
gzip 没解压，会把压缩内容当分片转发 推翻 Reply 不转发 Content-Encoding，且 Content-Length 按解压后的 body 重算 → 就算上游是 gzip 也是自洽的
处理完就 close，未声明 Connection: close 推翻 每一处响应头都带 Connection: close（grep 到 10+ 处）
局域网模式下 __vgproxy 可能被当免费代理 推翻 MediaProxy.handle 的调用点在口令校验之后，代码注释就写着"局域网访客不许拿它当开放代理"；且 enableLAN 会强制生成口令
进度/历史里存的是代理 URL → 重启后续看必失效 推翻 WatchProgress 存的是「键 → 秒数」（键是 lp/preview/任务 id）；WatchHistory 存的是 JS 上报的原始上游地址
黑名单缓存改了不生效，要重启 推翻 有 invalidateCache()，设置页改动与备份恢复处都调了
ucc 强引用 handler 造成永久泄漏（要把 handler 改成弱代理） 推翻 sleep() 里移除 handler ＋ t.webView = nil ＋ 清 byWebView，环断得干净（残留的"只摘一个"见成立表第 16 条，属轻微）
自检连接会占满 backlog → 引发"重启风暴" 推翻 backlog 32，且自检的连接会被 accept 立刻收走（recv 返回 0 就关闭），不会堆积（但"假阳性"那条成立，见成立表第 3 条）
socket write 的返回值没检查，断了也不知道 推翻 writeAll 检查了 n > 0 与 EINTR，返回 Bool
#EXT-X-BYTERANGE 会被改写破坏 推翻 该标签里没有 URI（形如 #EXT-X-BYTERANGE:长度@偏移），改写不碰它；Range 本来就是透传的

四、三家的「只能改 3 处」对比

#DeepSeek豆包MiMo
1 端口固定 + 健康检查改成真 HTTP 请求
"播放链路最致命的"		 给并发队列加闸门（16~32）＋ 顺手修无锁读 （输出被截断，未给出明确三条）
2 静态表加锁 + 上限 + TTL + 换更强的键 分片改流式转发 ＋ 拒绝 HTML 冒充媒体

五、我的结论与建议

建议分两批修

批次内容为什么
第一批（P0，小改大收益） 1. 普通模式优先固定端口（18080 起）；
2. 自检改成真 HTTP 请求；
3. 刷新条件改成"未重试过就刷新"（修二次 403 死路）；
4. proxyString 加 scheme 白名单；
5. 网络变化时清空 refreshed。 		全是几行到几十行的改动，不动架构，直接消灭两条 P0 + 一条 P1
第二批（结构，要设计） 6. serve 加并发闸门；
7. 播放代理独立 URLSession；
8. 静态表加上限 + TTL；
9. 刷新时同时比对 host；
10. 拒绝 text/html 冒充分片。 		要动到并发与连接管理，改完必须真机压测（多标签 + 边下边播 + 局域网同时开）

不打算动的

  • 分片流式转发（豆包的第 2 条）：收益是内存峰值，代价是把整个代理层从"同步取回"改成流式， 会牵动 Reply 结构和 socket 写出路径 —— 风险大于收益，先记着。
  • 视频历史的两个"误合并"：那是当初为满足你"宁可留一条重复也不要误并"刻意设的保守判据， 不改。
  • 局域网明文 HTTP、page world 注入页面 JS、用户脚本空 @match 兜底成全网 —— 都是明知并接受的取舍。

一句话

这轮最有价值的产出不是"发现了多少 bug"，而是把两条真 P0 从"偶发、说不清"变成了"能指到那一行"： 一条是端口漂移（你之前实测的 -1004 就是它），一条是刷新条件的布尔写错。 另外 15 条推翻的也说明一件事 —— AI 评审必须逐条对源码核，直接照做会白改。

核实方法：每条主张都在 app/*.swift 与 resources/*.js 里找到对应实现或反例， 附文件与机制；不确定的标注为不确定。
