磁力实测诊断：为什么效果差 / 能修到什么程度

会诊对象：v1.0.248 真机实测 —— 「好多链接只有 1 条能出文件列表；成功那条 4-5MB/s 掉到几十 KB/s； 大多『连上 peer 但列表一直加载』或『已连上 0 个』」
所有结论都对着 我们的源码 + libtorrent 官方构建文档核过；核对不实的地方单独标注，没编。

先给结论（四条）

  1. 成绩差里，相当大一块是我们自己的问题，不是 P2P 天生这么烂。 查出来 4 个硬伤（第三章，都有实据），其中最大的一个可能出乎你意料： 每开一条新链接，我们都会把整个引擎连根拔掉重建 —— 所以每测一条，网络能力都回到零点，头一两分钟基本是「还没接通」的状态。
  2. 修完的现实预期：热种（有人在下的）→ 列表几十秒内出、速度能打到资源带宽上限 （你已经见过 4-5MB/s，说明管道本身没问题，这点很重要）； 冷种（没人做种的）→ 谁都难，夸克也只是靠「它库里有」。
  3. 「像夸克迅雷那样：秒出 + 恒速 + 后台下」—— 纯客户端做不到等效。 那是服务端离线下载能力（第四章讲清为什么）。我们做的是「P2P 下载器」， 对标对象是 qBittorrent 这类，不是夸克这类「网盘」。
  4. 「能播」（边下边播）：当时拍板没做。它比下载更吃速度 —— 先把「找得到、下得动」修稳，再谈它。

一、你反馈的四个现象 → 逐条归因

你看到的现象表层原因底下是哪个硬伤
大多「找不到资源 / 已连上 0 个」 引擎还没接进 BT 网络（DHT 正在冷启动）+ 磁力自带 tracker 死了 硬伤①硬伤④ 同伴来源太少、且每次从零开始
「连上 peer 但文件列表一直加载」 连到的那几个同伴手里也没有清单 / 不给 硬伤①硬伤④ 同伴太少，碰不上「有清单的那位」
好多链接只有 1 条能出列表 那条恰好 tracker 还活着 / 种还热 低概率被 ①-④ 放大成大面积的「不行」
成功那条 4-5MB/s → 几十 KB/s 高速来源断开 / 被限速，没有后备同伴顶上 硬伤①硬伤④；另有 1 条待确认项（见第五章）

二、为什么「连上了」也拿不到文件列表？（大白话）

关键认知：磁力链接本身不带文件清单。

  • 磁力链接只是一串「身份证号」（info-hash）——它告诉别人「我要哪份资源」，但不包含文件列表。
  • 文件清单（种子里那些文件名/大小）要从「手上已经有清单的同伴」那里换过来。 两个都没有清单的人互相连上，也换不出清单。
  • 所以「连上 1-2 个、列表还是不出来」不是坏了 —— 是「连到的这几位刚好都没有 / 不给」。要同伴足够多，才碰得上「有清单的那位」。
  • 同伴从哪来？两条路：① tracker（约人点：链接里 tr= 那些服务器）； ② DHT（不用服务器、同伴互问的「电话簿」）。

我们现在的状况：磁力自带的 tracker 常常整批是死的； DHT 又每次都从零冷启动（硬伤①）—— 两个来源都处在最低配状态。这就是「成功率那么低」的结构性原因。

四、夸克 / 迅雷为什么「什么都能秒出」？（如实说）

  • 他们的「秒出文件列表」不是本事，是库存 —— 服务器库里存着这份清单 （之前有用户下过、或他们的离线系统抓过）。你贴链接，服务器一查库就有。
  • 速度稳 = 文件在服务器上（离线下好 / 缓存），你从服务器拉 —— 相当于「网盘下载」，不依赖「还有没有人在做种」。
  • 后台能下 = 下载跑在服务器上，你手机只是个遥控器。
  • 我们（纯客户端）三者都做不到等效 —— 这是产品类型差异，不是技术高下：他们是「网盘 + 离线下载」，我们是「P2P 下载器」。 qBittorrent 这类纯下载器，也做不到「秒出」。

但有个公平对照的问题要说清：拿「夸克能秒出的链接」来测我们才公平 —— 这类链接至少说明「网络里还有热度 / 库里还有货」。如果修完硬伤之后，连这批链接都出不来， 那时才轮到怀疑更深层（运营商干扰 BT 流量这类环境问题）。

五、「4-5MB/s 掉到几十 KB/s」的专门解释

好消息 起步能跑 4-5MB/s = 你的手机、我们的引擎、整条链路都具备跑高速的能力。管道没问题 —— 这一条恰恰证明「多连同伴」是这个引擎值得投资的方向，而不是引擎本身不行。

掉速机制 给你供速的那台做种机（能从 4-5MB/s 起步，大概率是服务器型做种机）断开、或把上传让给了别人； 而我们没有后备同伴顶上（硬伤①④）→ 速度塌方。

待确认 iOS 会在 App 进后台几十秒后冻结网络 —— 如果测的时候你切出去过 / 锁过屏，速度会断崖式掉。 这条没有实据，需要你回忆确认一下。

下次实测 请顺手记两个数：掉速 / 失败那一刻的「已连上 N 个」和「DHT N 节点」 （v1.0.248 的界面上就有，就是为这个排查加的）。

七、建议（待你拍板，我不先动手）

P0 —— 建议一版全修，预计显著改善：

  1. 重编 libtorrent：加密开回来（3 分钟，零风险；顺带把「加密需要 OpenSSL」这个错误判断修正）
  2. 引擎常驻化：开新任务不再重建网络（改动中等，收益最大）
  3. DHT 状态存盘：打开 App 就是「热网络」，不再每次从零爬

P1：

  1. tracker 列表扩充 + 动态更新（几十条、定期刷新）
  2. （可选）多任务并存

P2 备选：本地清单缓存（同一链接第二次 → 秒出）。

验证方式：出下一版后，用你的「夸克对照链接」重测一组， 看三个指标：① 出列表要多久 ② DHT 节点数 ③ 速度峰值。

要你配合两件事 ① 给我 3-5 条「夸克 / 迅雷能秒出文件列表」的磁力链接（做公平对照的标尺）；
② 下次实测时保持 App 在前台；失败 / 掉速那一刻，截「已连上 N / DHT N 节点」两个数给我。

八、一句话总结

不是「根本做不到」，是「背着四个沙袋在跟职业选手比」。

先把沙袋卸了（P0 三条），卸完还差的，才是真正属于「纯客户端 vs 服务器」的物理差距 —— 那部分不接服务端就追不平，我如实说在前头。
