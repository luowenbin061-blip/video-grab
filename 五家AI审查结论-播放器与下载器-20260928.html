一、成立（已回源码核实）

级别问题证据（文件 · 行）建议改法
P0 回归：清单里的相对 URI 会被指到本机服务上
清单搬到本机 http 后，任何相对地址的解析基准都变了。原来在远端好好的 #EXT-X-KEY:METHOD=AES-128,URI="key.bin"、#EXT-X-MAP:URI="init.mp4"（纯 ASCII）会被原样保留， 于是播放器去请求 http://127.0.0.1:端口/key.bin → 404 → 把本来能播的流搞坏		 PlaylistRelay.swift（v1.0.139 原写法）：
guard uri.contains(where: { !$0.isASCII }) else { return line }
调用点只认：line.hasPrefix("#EXT-X-KEY")		 已修：换成 rewriteURIAttrs，对所有 # 行里的 URI="…" 一律绝对化（#EXT-X-MAP/#EXT-X-MEDIA 等也覆盖），并加进自检 R8/R8b/R8c
P0 回归：临时清单可能在播放中被删
旧逻辑"超过 1 小时就清"—— 而 AVPlayer 播放 HLS 期间会重新请求清单（seek 之后尤其明显）， 那份清单一旦被删就是 404 / 拖进度条黑屏		 PlaylistRelay.cleanOld +
static let staleAge: TimeInterval = 3600		 已修：文件名改成按远端地址算出的稳定名（同一部片子每次同名 → 根本不堆积）， 保留期放宽到 7 天，播放中绝不可能被删
P0 探测大文件时可能把整份文件读进内存
发了 Range: bytes=0-2047，但只要服务器忽略 Range 回 200， data(for:) 就会把整个响应体读进内存。探测一个 1~2GB 的 mp4 直链 → 直接被杀		 SourceProbe.swift：
let (data, resp) = try await URLSession.shared.data(for: r)
（同文件里 Range 只"请求"了，没有防御性校验）		 改成流式：先 HEAD，或用 URLSession.bytes(for:) 只读前几 KB 就取消； 绝不能假设服务器会遵守 Range。（FileDownloader 已经在 v1.0.101 修过同类问题，探测这条路漏了）
P1 拼接时缺分片被静默跳过，而完成判据是"自洽"的、发现不了
缺分片就 continue；随后 fileSize == joinedBytes 两边本来就是同一个数，恒等成立 → 缺了内容也会被判定"拼接校验通过"，写完成标记、清分片、继续转 MP4		 Downloader.swift:213
guard let data = try? Data(contentsOf: part) else { continue }
DownloadJob.swift：if joinedBytes > 0, fileSize == joinedBytes { … }		 缺分片必须抛错（throw Fail.missingSegment(i)）；完成判据换成 "实际写入分片数 == 期望分片数"，别拿两个同源的数互相比
P1 分片下载没有内容校验
只要 HTTP 2xx + 非空就落盘。服务器回一个 200 的错误页/拦截页，也会被当成分片写进成品 → 拼出来的 .ts 是坏的，只有 FFmpeg 失败才能"偶然"拦住		 Downloader.swift:336-342：
只判 !(200...299).contains(statusCode) 与 guard !data.isEmpty， 不看 Content-Length、不看内容类型、不看首字节		 至少加两条：① 已知 Content-Length 时比对字节数；② 首字节必须是 TS 同步字节 0x47 （这条本项目已经有现成实现：LivePreview.blockReason 里就是这么判的）
P1 断点续传判据只有"文件存在且 >0 字节"
上次拿到一个短响应（200 但内容不全）会被永久当成完整分片，以后再也不重下		 Downloader.swift:330：
if let sz = try? …[.size] as? Int, sz > 0 { return 0 }		 记下每个分片的期望大小并比对；或给分片单独写"完成标记"（跟成品那套 joinedMarker 同思路）
P2 本机服务的 Range 处理不符合 HTTP 语义
bytes=100-50（start>end）、bytes=0-1, 3-4（多范围）、bytes=-0 都不回 416， 而是返回从 start 到文件末尾、甚至整个文件		 LocalHTTPServer.swift Range 解析段：
if comps.count > 1, let e = Int(comps[1]), e >= s { end = min(e, total - 1) } （e < s 时不改 end，沿用初始的 total-1；"1, 3" 令 Int() 失败 → 同样落到整个文件）		 非法范围 / 多范围一律回 416。播放器是会发 Range 的，返回错数据比返回错误码更难查
P2 地址清洗的两个死角
① 快路径只查"全 ASCII 且无空格"，会放过无效的 %（如 100%.ts）→ URL(string:) 依旧返回 nil（老失败模式复活）；② 保留 # 会让文件名里的 # 变成片段， 请求路径被切断（视频#1.ts → 实际去要 视频）		 M3U8.swift：
if s.allSatisfy({ $0.isASCII && $0 != " " }) { return s }
保留字符表里含 #		 ① 快路径也检查"每个 % 后面是不是两个 hex"，不满足就走慢路径； ② # 一律编码成 %23（片段本来就不会发到服务器，编码它只会更安全）
P3 目录穿越防护不解析符号链接
standardizedFileURL 只做路径规范化，不会解析符号链接； 下载目录里若存在指向外部的软链，检查能过、实际读到外部文件		 LocalHTTPServer.swift 防穿越段：
let target = root.appendingPathComponent(path).standardizedFileURL		 比较前先 resolvingSymlinksInPath()，或显式拒绝符号链接。（自用场景低危，但顺手能修）

二、推翻 / 需要限定（AI 说得不对或不完整）

AI 的说法核实结果
「分片写一半残留会被当成完整分片」 部分推翻：data.write(to: dest, options: .atomic) 是原子写，自己崩不会留半截文件。 真正的缺口是"服务器给了短响应"（见成立 #6），不是"写一半"。
「sizePoller 这个 Task 可能跑在主 actor 上，造成界面卡顿」 推翻：FFmpegConverter.toMP4 是 nonisolated 静态函数，里面的非结构化 Task 不继承 actor， 跑在全局并发执行器上；而且每 500ms 才一次回调，够不上卡顿来源。
「GBK 清单可能碰巧是合法 UTF-8 从而被误解码」 推翻（概率可忽略）：整份含中文的 GBK 字节序列同时构成合法 UTF-8 基本不可能； 真失败会自动落到 GB18030 那一层。
「beginStallWatch 只依赖通知，会漏掉"通知没发但一直不前进"」 推翻：它本来就是独立的 8 秒计时器，不靠通知。AI 是没看到那段代码（简报里没贴），属材料不足导致的误判。
「LocalHTTPServer.shared.start(root:) 若"第一次生效"会导致清单 404」 修正：实现是每次调用覆盖 self.root = root。所以真实风险反过来了 —— 播放中若另一个模块用别的 root 启动过服务，正在播的清单会失效。目前所有调用方都用同一个下载目录， 所以暂时不出问题；值得加一条"root 变化时拒绝"的断言。

三、"先修哪 3 个"—— 我的排序（与 AI 不完全一致）

  1. 探测阶段的内存炸点（P0） —— 直接对应你说的"大文件卡死/被杀"，改动小、收益大。
  2. "缺分片 / 错误页也能报成功"这一整条链（P1×3） —— 这是最恶劣的一类错误（数据不可信）。 三处要一起改：拼接必须抛错、完成判据要换成计数、分片要校验内容。
  3. 本机服务 Range 语义（P2） —— 播放器在用它，返回错数据会表现为"播到一半出问题"，很难查。
两个 P0 回归（清单 URI / 清理时机）我已经当场修掉了 —— 那是我这一版新写的东西自己带的坑， 不等你确认。其余几条我先不动：它们动的是下载主链路的判据，改之前想跟你确认一次改法。
