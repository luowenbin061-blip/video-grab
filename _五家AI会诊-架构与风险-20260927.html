先看结论

如果只做 3 条（我按"踩坑概率 × 修复成本"排的）

  • P0-1 崩溃与卡死的"现场留证"：现在只有"主线程最长失联时间"这一个数字， 没有任何崩溃捕获（全项目搜不到异常钩子/崩溃日志）→ 悬案永远只能等下一次。三家独立命中
  • P0-2 JS→原生桥的信任边界：任何被注入的页面都能直接触发"下载"（含往本地 WebDAV 读写）， 没有任何来源校验或频率/大小上限 → 被挂马的页面可以刷满你的磁盘、或把本地服务当跳板。本次最有价值的新发现
  • P1-3 全局下载调度 + 网络感知：分片并发写死 4、没有全局上限、没有"同域名限制"、 没有"蜂窝/低电量不自动下" → 多任务互相抢带宽、发热、更容易失败。三家独立命中

表 A · 成立（确实缺，按优先级）

优先级建议类别现状与证据怎么改 / 代价
P0 卡死悬案：从"只记时长"升级到"当场留证"
通义 + MiniMax + DeepSeek 三家		 稳定性 现在命中的是"事后一个数字"：过程记录里有"主线程最长失联"，但失联超阈值时不会主动抓现场； 全项目搜 crash.log / NSSetUncaughtExceptionHandler / callStackSymbols 零命中 —— 也就是说崩溃类问题现在连日志都没有。 心跳（已有）加一条：失联 >5s 就异步 dump（任务阶段 + 内存 footprint + 主线程栈 + 正在写的文件偏移）， 原子写盘；再补一个 NSSetUncaughtExceptionHandler + signal handler 写本地崩溃文件。 代价：dump 本身要用低优先级线程、信号安全写法，别把卡死变成卡更久。
P0 JS→原生桥加信任边界
MiMo（独特）+ DeepSeek 部分		 数据安全 sniffer.js 通过 vgSniff 上报（BrowserModel.swift:566 注册）， 原生侧接上就建任务（网页触发下载 onFileDownload）。没有来源校验、没有频率/单任务大小上限。 本地 WebDAV 又是带口令的 http 服务 → 一个页面既能刷盘，也能拿这个服务当内网跳板。 ① 原生只接受"元数据 + 白名单字段"；② 网页触发的下载要求最近有真实用户手势（时间窗）； ③ 加"每分钟最多 N 个任务 / 单文件最大 X GB"的闸门；④ 本地服务对 loopback 来源也校验口令。 代价：极少数站点需要"自动下载"，可白名单。
P1 全局下载调度 + 网络感知
三家独立命中		 性能 / 成功率 并发写死：DownloadJob.swift:695 concurrency: 4；没有全局上限、没有按域名限制； 全项目搜 NWPathMonitor / isExpensive / 低电量 零命中 → 蜂窝下也会照跑。 加一个调度器：全局最大连接（6 左右）、同域名 2～3、失败指数退避 + 抖动； 蜂窝/低电量时不自动开始（要下给用户点一下）。 代价：理想网络下速度略降；调度逻辑要压测。
P1 HLS 的 fMP4（EXT-X-MAP）落到下载链
DeepSeek + MiMo		 下载成功率 M3U8.swift:40/57/106 已经解析了 EXT-X-MAP（fMP4 的初始化段）， 但下载/拼接走的是自写 TS 那条路 —— 遇到 fMP4 源（越来越多站点用）有产出坏文件或静默截断的风险。 下载链先做"能力判定"：识别不了就明确报错（"这个流是 fMP4，暂不支持"）， 别产出坏 MP4；有余力再补 init 段 + fMP4 拼接。代价：报错会显得"能力变少"，但比给坏文件强。
P1 PiP 保活失效后的降级与提示
DeepSeek + MiniMax		 稳定性 保活全靠画中画小窗：被用户划掉、被系统回收、音频会话被别家抢占时， 下载任务这条没有明确的"停 + 告诉用户"（v1.0.104 只处理了"划掉小窗 → 关共享"）。 监听 PiP 结束（pictureInPictureControllerDidStopPictureInPicture 已用过）→ 主动暂停任务 + 本地通知；可考虑 remux 阶段申请 BGProcessingTask 兜底（不确定在 TrollStore 环境是否稳定）。
P2 POST 表单触发的下载
DeepSeek（独特）		 下载成功率 全项目搜 httpBody 零命中：WKNavigationResponse 只能拿到响应，拿不到 POST body → 站内"表单导出 / 提交式下载"这类会失败。 short 期：这类情况给明确提示（别静默）；长期：JS 侧 hook form/fetch，把 method + body 摘要上报，原生用 URLSession 重放。 代价：body 可能很大 + 安全边界要重新想。
P2 播放前探测 + 失败可解释
DeepSeek		 交互可用性 FFmpeg/ffprobe 符号是链进来的（Hook.m），但只在取时长/分辨率时用； AVPlayer 播不了时界面只给一句"播不了"，没有"为什么 / 我能不能先转码"。 播放前用 ffprobe 探一次（容器/编码/音轨），不支持就提示并给"转 MP4 后再播"的按钮；字幕单独列一档（现在没有）。
P2 局域网服务的 keep-alive
MiniMax（说对了一半）		 稳定性 / 播放 Range / HEAD / 206 其实都有（见下表 B），但没有 keep-alive： 本地服务每个请求都要重连，AVPlayer 频繁 seek 时收益明显。 加 Connection: keep-alive + 循环内复用连接；顺手给 socket 加读写超时。 代价：连接生命周期管理，别把线程占住。
P2 落盘格式加版本号
通义 + MiniMax		 数据安全 原子写其实早就有（见下表 B），但没有 schemaVersion： 现在靠"加可选字段 + 读不到就兜底"来兼容（JobRecord 的 paused / kind 就是这么加的）。 字段一多，这种"靠约定"的做法迟早出乱子。 给每个 JSON 落盘文件顶层加 version，读时做一次性迁移。代价：小，收益长期。
P2 任务查重
我补的（AI 没提）		 交互可用性 书签有去重（Bookmarks.swift:313），但下载任务没有： 同一个地址连点两次就建两条任务、下一份重复文件。 建任务前比一次 sourceURL（已存在就提示"已经在下了/已下过"）。代价：一行判断。
P3 DASH / blob 两条已知盲区 下载成功率 已知未做：DASH（mpd）完全不支持；blob: 只给提示。 （注意：blob 播放的视频其实已经能救 —— v1.0.105 的 pickAlt 会从 hook 记录里找可下的真实地址； 真正没做的是"blob 本身就是下载目标"这类，如站点导出功能。） DASH 是"最小可用版本"级别的活（非 DRM 才有意义）；blob 可做"页面内分片转 base64 回传"， 但内存与成功率都不划算 —— 我倾向先明确报错，不做。
