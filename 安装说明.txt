文件    VideoGrab 目录根下 VideoGrab-unsigned.ipa（固定名字，每次构建自动刷新）
仓库    https://github.com/luowenbin061-blip/video-grab
构建    2026-09-25  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.77 = 控制条同步重做：查清系统那套显隐机制，把"慢 0.2~0.3 秒"的四层自伤全拆掉

────────────────────────────────────────────────────────────
一、先说查到的两条硬事实
────────────────────────────────────────────────────────────
 ① **"挂进系统控制条的显隐动画"这条路在 iOS 上是封死的。**
  查了 Apple 文档原文：`willTransitionToVisibilityOfTransportBar` 的可用性写的是
  **tvOS 11.0+**，iOS 不在列；配套的 `AVPlayerViewControllerAnimationCoordinator`
  这个类型在 iOS SDK 里根本不存在（连编译都过不了）。
  （网上有说法称"iOS 上其实有效"——**那个说法是错的**，我核对过文档。）
 ② **系统的显隐是靠视图透明度变的，而"读透明度"本身一点都不慢。**
  关键事实：UIKit 动画会在动画**开始**那一刻就把 model 值设成终值，
  真正在屏幕上渐变的是**呈现层**。所以读 `view.alpha` 拿到的是"目标"（甚至比视觉更早），
  读 `layer.presentation()?.opacity` 才是"屏幕上现在的样子"。

────────────────────────────────────────────────────────────
二、那 0.2~0.3 秒是怎么来的 —— 全是我自己叠的
────────────────────────────────────────────────────────────
   手指一按就冻结读数                 → 起步就停
   松手后还要等 0.2 秒才解冻           → 200ms
   采样间隔 100ms                     → 平均 50ms
   阈值 0.8（等系统动画快走完才认）    → 约 100ms
   去抖（要求连续两次读数一致）        → 再加 100ms
                               合计 ≈ 250~400ms（正好是你感觉到的那个数）

 **这不是系统的问题，是我一层层加"保险"加出来的。**

────────────────────────────────────────────────────────────
三、这版怎么改（净删，不是再加一层）
────────────────────────────────────────────────────────────
 · 采样 100ms → **33ms**
 · 改读**呈现层**的实际透明度（屏幕上真值），不读 view.alpha
 · 判定阈值 0.8 → **0.05**（系统刚开始出现就跟上，也不会在过渡中间来回抖）
 · 去抖只留"连续两次一致"（33ms×2 = **66ms**，滤单帧抖动，人眼分辨不出）
 · **删掉整套「按下冻结 / 松手等 0.2 秒 / 解冻定时器 / 统一解冻回调」**
   —— 那套当初是为了躲"滑动时闪"，而那个闪的真根因（点击乐观切换）已经删掉了，
   保险早就该撤；留着反而是这轮"慢"的主因。
 · 这几样**保留**（都是你明确要过的）：调进度时按钮不许出现、点击不做本地切换、
   万一读不到系统状态就退回自算那套（不会让人卡住）
 · 横屏位置（距安全区左 158 / 上 47）和图标 18pt **一个字没动**

 预期：「点一下 → 图标变化」从约 250~350ms 压到 **≤66ms**，肉眼与系统同步。

────────────────────────────────────────────────────────────
这一个是上一版我自己加的"乐观切换"惹的
────────────────────────────────────────────────────────────
 现象（你报的）：交替点播放按钮和暂停按钮，横竖屏图标反复显示、消失。

 根因：上一版为了让点击"显得灵敏"，我让点击**本地切换显隐**（亮着就收、藏着就亮）。
 但这一指可能落在系统按钮上（播放/暂停、快进、音量、进度条…），也可能是点空白处要
 切换控制条 —— 我们这一层**分不出来**（读不到系统按钮的位置）。于是每点一次就反转
 一次：交替点播放/暂停 → 图标反复显隐。你自己分辨过**系统控制条是稳的**，
 只有我们在动 —— 这条证据直接把它定在我这边。

 改法：能读到系统状态时，点击**不再做任何本地切换**，只把这一指交给系统 ——
 它该怎么收就怎么收（点完停一会儿，3 秒后收起），点空白处它自己切换，我们跟着就是。
 唯一例外：完全读不到系统状态时（私有读法失效、退化到自算那套）保留本地切换，
 否则那条路上点击会彻底没反应。
 顺手把解冻时间 0.25 → 0.2 秒（点空白处要切换时别显得迟钝）。

 为什么这次不再"乐观"：上一版乐观是为了手感，实际上是在跟系统抢同一件事。
 系统这套显隐已经做得又准又完整（含 3 秒倒计时、点播放暂停不收那些细节），
 我们唯一该做的是**跟随** —— 重做一遍必然在细节上跟它打架。

────────────────────────────────────────────────────────────
一、位置：不是调数字的事，是我上一版用错了基准
────────────────────────────────────────────────────────────
 实测（你的截图，scale≈1.39）：
   左上 ✕ 屏幕 55pt ／ 左上小窗图标 107pt ／ 我们的箭头 **206pt**
   → 间距：✕→小窗 52pt，小窗→我们 **100pt**（差了近一倍，你说"太大"完全对）

 根因：**系统的图标是按「屏幕」摆的，而我的代码是在「安全区」里定位的**
 （横屏时刘海那一侧的安全区约 48pt）。我上一版写的是"距安全区左 158pt"，
 落到屏幕上就变成了 206（158 + 48）—— 多出来的那一截就是你觉得太大的间隔。

 改法：position 里减掉**窗口真实的安全区宽度**（直接读系统给的数，不猜机型）
 → 换算回屏幕坐标，落在 **158pt**（= 小窗 107 + 系统那排的间距 51）。
 横向不需要避让刘海：横屏顶部工具栏那一带本来就没有刘海。
 **竖屏一个字没动**（你说 OK 的那组：距右 113 / 距下 53）。

────────────────────────────────────────────────────────────
二、图标 21pt → 18pt
────────────────────────────────────────────────────────────
 量的结果：左上 ✕ 视觉 15pt、小窗图标 20pt、我们的箭头 19.5pt
 —— 数值上跟小窗差不多，但它是两条**张开的斜线**，看着比小窗"大一圈"。
 取 **18pt**（视觉约 16.6pt），正好落在 ✕ 和 小窗 中间。这是你选的档。

 觉得还是偏大/偏小，说一声（两个数字的改动）。

────────────────────────────────────────────────────────────
三、右滑时"一闪一闪"：根因在我这边（你确认系统控制条是稳的，这条证据很关键）
────────────────────────────────────────────────────────────
 根因：**手指一按下去，系统可能正把控制条点亮**（左右滑动调进度就是这种情况），
 我不冻它就会先跟着亮一下、紧接着被滑动逻辑收掉 —— 那一亮一灭就是你看到的闪。
 左滑看着正常，只是因为落手更快、那个窗口没被看见（不能因为"左滑没事"就放过）。

 四处改：
 · **手指一按就冻结**：这段时间显隐只听我们自己的，不看系统读数（你说不要显示就不显示）
 · **松手后 0.25 秒才解冻**：躲开系统在松手瞬间的状态抖动；之后由系统读数接管
   （轮询 100ms 一次，解冻后最多 100ms 就同步上）
 · **读数去抖**：判定"控制条显示"的阈值从 0.5 提到 0.8（系统淡入淡出会经过 0.5，
   采样落在那儿就 true/false 反复），并且**连续两次读数一致才采信**
 · **删掉"拖进度条松手立刻恢复"那个特例**（你确认过）：拖进度条时系统控制条本来就
   是显示的，解冻后 ≤100ms 我们自动跟着亮 —— 效果一样，但不用再猜"手指起点在不在
   进度条上"。那个猜法正是右滑被误判、进而闪的来源。
 · 点击仍**立即响应**（本地先切，0.25 秒后交回系统读数确认）

 顺带补了一个自己挖的坑：长按不放再松手那条路，原来既不报点击也不报滑动 →
 冻结状态永远不会解除（读数被冻住）。现在手指离开一律解冻。

────────────────────────────────────────────────────────────
一、显隐：现在是真的"跟随系统"，不是我们照着规则猜
────────────────────────────────────────────────────────────
 你列的规则（刚进来不显示 / 点屏幕才显示 / 点播放暂停时保持 / 拖进度条时收起 /
 没触摸后自己收 / 没有淡出）—— 这些**系统本来就在做**，公开接口却拿不到它的状态。
 所以这版直接去读系统那个控制条的显隐（100ms 一次，**只读、不改它**），它怎么变我们就怎么变。

 · 全程**不做淡出**：立即显示、立即消失（你明确说过没有淡出这个概念）
 · 进来时不显示（系统的控制条一开始也是不显示的）
 · 拖动进度条：开始拖就收起来，松手立刻恢复并开始 3 秒倒计时

 ★ 安全网：这个读法是靠私有层级，万一哪天系统改了名字读不到，
 会自动退回我们"自己算"那套（点一下切换 / 拖动收起 / 播放中 3 秒 / 暂停常显）。
 而且**必须"看见过显示、也看见过隐藏"两种读数才承认它可信** ——
 免得读到个假值反而把按钮变成永远不亮（那就比现在更糟）。

────────────────────────────────────────────────────────────

────────────────────────────────────────────────────────────
 根因：上一版记了一个「我让它横了」的状态，图标按这个状态变；而转屏请求在弹层动画还没结束时
 会被系统丢掉 —— 于是图标先变了、屏幕没转，你就得再点一次。
 现在：**图标样式和点击动作都按"实际方向"判断**，并且转屏失败会自己补一次。

────────────────────────────────────────────────────────────
三、横屏位置：挪到最右边（省略号图标右边）
────────────────────────────────────────────────────────────
 量的结果（1184×546 截图）：系统那两颗已经贴在安全区右边界上了，再往右本来就没地方 ——
 所以新位置是「超出安全区右边界 22pt」：跟省略号保持约 32pt 间距、离屏幕右边还剩约 14pt。
 横向虽然进了刘海那条带，但刘海只占竖直方向的中段，而按钮在屏幕下方（约 78% 高度处），
 不会被挡。**竖屏位置没动**（你说 OK）；横屏下边距 +3pt 对齐系统那一行。

 装上如果觉得"太贴边"，跟我说一声：可以缩到更靠里一点，或者退回原来省略号左边。

────────────────────────────────────────────────────────────
 · 右下角那个圆按钮改成可选：设置 → 嗅探 →「嗅探按钮常驻屏幕」，**默认关**（不占地方了）
 · 打开嗅探结果的两个新入口：
    「功能」卡片（底栏那个 ≡）里一格「嗅探结果」（带条数徽标）
    工具箱 里一行「嗅探结果」

────────────────────────────────────────────────────────────
 你可能踩到的那个「未读取到切片」，根因找到了：
 **原来所有下载都塞给 m3u8 解析器** —— 碰到 MP4 直链、跳转页这种根本不是清单的地址，
 一个分片都解析不出来，只报一句失败，看不出为什么。

  · 下载前先「探一下」这个地址到底是什么（取前 2KB 看一眼）：
    是真清单 / 是单个文件 / 还是认不出。探测结果写进任务的「过程记录」。

  · **认不出 / 取不到** → 直接把「HTTP 状态 + 类型 + 内容开头 160 字」报出来，
    不再是没头没脑一句话。以后遇到下不动的，把那行发我，我一眼能定性。

v1.0.51（= WebDAV 第二档：手机变成电脑上的一个盘）

【以前什么样】
 同一 Wi-Fi 下电脑浏览器打开地址，能看到文件列表、点着下载 ——
 但只能看和拿，像隔着窗户看东西。

【现在什么样】
 手机能挂成电脑上的一个「网络磁盘」：出现在「此电脑」里，
 能拖文件进出、改名、删除，双击就用电脑自己的播放器播。

【电脑上怎么连 —— 两种办法，选一个】

 办法一（推荐，最省事）：装个 WebDAV 客户端
   · Windows：RaiDrive（免费版够用）或 Cyberduck
   · 填这三样（App 的共享页里都有，可一键复制）：
       地址 = http://192.168.x.x:18080/
       用户名 = 随便填
       密码 = 那串口令

 办法二：用 Windows 自带的「映射网络驱动器」—— 要多做一步
   Windows 默认只肯连 https 的 WebDAV，http 地址必须先改注册表：
     1) 开始菜单搜 regedit 打开
     2) 找到 HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\WebClient\Parameters
     3) 把 BasicAuthLevel 改成 2（没有这个值就新建一个 DWORD 32 位）
     4) 顺手把 FileSizeLimitInBytes 改成 4294967295（不然大文件传不动）
     5) 重启电脑（或者只重启 WebClient 服务）
   然后再用「此电脑 → 映射网络驱动器」填上面那个地址。

【需求 2 · 页面加载慢 / 滑动不跟手 —— 原因查出来了，是注入脚本】
  sniffer.js 里有两处硬伤，都压在热路径上：
   · 每轮扫描都把**整页 HTML 序列化成字符串**（几百 KB ~ 几 MB）再跑正则，
     而它挂在「每 1.5 秒」的定时器上；
   · DOM 监听没有节流 —— 页面每变一次 DOM 就跑上面那一整套，
     现代网页一秒能变几十次。
  两处叠加 = 每秒几十次全页序列化。这不是 WKWebView 天生慢。

  改法（按代价分三层）：
   · 轻活（媒体元素 + 页面全局变量）→ 定时器（1.5 秒 → 3 秒）和 DOM 变化照跑，
     且 DOM 变化合并 400ms 内的多次变动，只跑一次
   · 重活（整页序列化 + 正则）→ 只在页面加载完成后、你手动刷新/长按时各跑一次
   · 首扫从「脚本一注入就扫」推到 DOM 建好之后（原来那次 DOM 还是空的，纯白跑）
   · 上报加 500ms 最小间隔（原生每收一次都要重排整个列表）
   · 补上 src 属性监听 —— 有些播放器用 setAttribute 写地址，
     原来靠 1.5 秒定时器的全量扫兜着，现在显式补上（不丢能力）

  顺带一个实测发现（也是本批唯一被自己推翻的东西）：
  我一开始还加了「先用 indexOf 预筛、没有扩展名就跳过正则」，理由是「省一次正则」。
  实测五个真实页面：全量正则平均 0.11 ms，预筛 0.206 ms —— 预筛要扫 6 遍、正则只扫 1 遍，
  加它净亏。所以撤掉了。注释里留了数据，免得以后又被「看起来能省一点」的直觉带回去。

  WebView 那边配置本来就是齐的，唯一能改的是**预热**：App 一启动就先加载一次空白页，
  让 WebKit 提前把网页进程拉起来 —— 你第一次真正打开网页时就不用等这套冷启动。
  （Safari 的进程一直是热的，这是它在首屏上快的原因之一，也是我们能自己消掉的一段。）

【需求 1 · 任务切换器卡片没图标 —— 这条我前面诊断过两次，第二次是对的】
  第一次：拆包看到「只有 AppIcon60x60@2x.png、没有 @3x」，判断是图标缺尺寸。
  第二次：把 18 张图标（含 180×180 的 @3x）全塞进去重新构建，actool **依然只导出 @2x**
         → 于是改口说「这是 actool 的既定行为，包里的图标本来就是好的」。
         **这句改口推早了** —— actool 不导出，不等于系统不去要那张文件。

  现在为什么又回到这条：看你那张截图，同一屏里别的 App（App Store 装的）图标正常，
  只有我们空白 ⇒ 不是全局图标缓存，是这个包在某条查找路径上拿不到图。
  而我们自己：**主屏图标正常、只有任务切换器空白** —— 这两处走的是不同的路径：
    · 主屏 → Asset Catalog（CFBundleIconName = AppIcon）→ 一直没问题
    · 任务切换器 → 老式路径，按 Info.plist 里的**基础名**去找松散 PNG 文件
  而 `CFBundleIconFiles` 存的正是基础名：
      iPhone: [AppIcon60x60]        iPad: [AppIcon60x60, AppIcon76x76]
  老式路径拿它按屏幕倍数拼文件名：@2x 设备要 `AppIcon60x60@2x.png`（有），
  @3x 设备要 `AppIcon60x60@3x.png`（**没有**）。@3x 正好就是 iPhone。
  拿不到 → 画成系统占位网格。这条能同时解释「主屏正常、切换器空白」。

  → v1.0.40 的改法：在云端构建时、**签名之前**，把图标复制成那几个老式文件名塞进 .app
    （签名之后再加文件签名就失效了，所以这一步的位置很讲究）：
      AppIcon60x60@2x.png      120×120
      AppIcon60x60@3x.png      180×180   ← 关键，以前包里完全没有
      AppIcon76x76~ipad.png     76×76
      AppIcon76x76@2x~ipad.png 152×152

v1.0.36 做过什么（保留备查）
────────────────────────────────────────────────────────────
把画中画这个问题拿去问了五家 AI，按他们的一致结论改

【五家 AI 的会诊结果：三条实质答案，两条结论独立撞在一起】

◆ 结论一（两家分别独立得出，说法几乎一样）：
  真正的病灶不是「场景类型」，而是 **承载画面的那个视图根本没进到前台活跃的窗口里**。
  原话：「你用 UIViewRepresentable 的 .background 挂一个 3×3 的视图，
  makeUIView 返回时 view.window == nil，content source 关联到一个无窗口的层，
  AVKit 记下的场景关联从一开始就不合法 —— **懒创建或重建都没用**，
  因为重建时机同样早于 didMoveToWindow；而且 3×3 不满足『inline 视图非零』的隐含要求。」

  → 这一版：不再让 SwiftUI 承载那个视图，改成 App 自己把宿主视图（180×101，明确非零）
    加到 keyWindow 的**最底层**（被上面不透明的页面盖住，你看不见它）；
    要建控制器之前，先确认层真的已经在窗口里，不满足就等，不浪费尝试次数。

◆ 结论二（第三家）：
  「送帧必须走固定节奏，而且**与启动重试各走各的**。你那个梯子间隔最长到 2 秒，
  等于在饿着层；层长时间收不到帧会自己进 failed（-11847），层一旦 failed，
  后面重试多少次 start 都不会成功 —— 这就是『重试 10 次全失败』的一个很可能的原因。」

  → 这一版：送帧改成**每 0.35 秒一帧**的固定节奏，在点开关时就开（不再等小窗起来才开），
    并且挂在 RunLoop 的 common 模式上（滚动页面时也不断）。

◆ 结论三（判断后决定不换路）：
  视频通话那套（AVPictureInPictureVideoCallViewController）**不能绕过这个错误** ——
  两条路都要求 start 那一刻场景是前台活跃。而 Stay 用的正是我们这条路
  （它要完全控制帧的时序和分辨率）。所以继续走这条路，不折腾。

【这一版其它小改动】
  · 第一级启动延后 0.6 秒（不贴着确认框关闭那一瞬间调）
  · 每级尝试前先确认场景是前台活跃，不在就等（不消耗尝试次数）
  · 重试从 10 次拉到 12 次（约 10 秒），中途整个重建一次
  · 还是不行的话，报错会带上：层状态 / 场景状态 / 音频会话 / 系统原话

【怎么测（顺序依旧）】
  1. 删旧版再装。进 App 等两秒
  2. 点「PIP 后台下载」→ 确认框点「好的」
  3. 小窗可能一秒左右才出现，别重复点
  4. 起来后：去点下载 → 切后台/锁屏 → 进度继续跳

      iOS 把它当成「正在播放的媒体」，于是继续给运行时间。
      这比「放一段无声音频骗系统」干净 —— 那招会被静音检测杀掉。

怎么用：正常点下载 → 直接切后台 / 锁屏 → 会出现画中画小窗。
       回前台它自动收起。
       画中画上那个播放/暂停按钮没用（下载没法暂停），忽略即可。

出问题时：界面底部会显示画中画起不来的具体原因（不静默失败）。

一个说明：从多任务里上滑「杀掉」App，画中画也会一起没 —— 这是系统边界，
         下一版会用后台传输通道（URLSession 后台会话）补上这一层。

这一版 = 换引擎
────────────────────────────────────────────────────────────

你的实测给出了决定性证据：同一个 .ts，别的转码软件几秒转完
（有声有画面）→ 下载和拼接完全没问题，问题全在我手写的
重封装器上。

所以这版不再自己写 —— 直接内嵌 FFmpeg 引擎（Stay、亚瑟、
各类下载器 App 内部用的同款引擎），转码改用：

    ffmpeg -i 输入.ts -c copy -movflags +faststart 输出.mp4

`-c copy` = 只换容器不重编码：
  · 秒级完成
  · 音轨原样保留（ADTS/B帧/LATM/HEVC 全由 FFmpeg 处理，
    覆盖面比我手写的解析器大几个数量级）
  · +faststart 把索引挪到文件头 → 拖进度条秒响应
  · 完成后自动体检输出文件，过程记录写明：视频轨 ✓/✗、
    音轨 ✓/✗（含采样率声道数）、时长

代价：IPA 从 0.4MB 涨到 9.2MB（FFmpeg 引擎的体积）。
