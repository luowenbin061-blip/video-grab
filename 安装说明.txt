v1.0.35 = 画中画第四次修：content source 改成「用的时候才建」

【你的报错终于把真话说全了】
  AVKitErrorDomain -1001: Failed to start picture in picture. /
  The UIScene for the content source has an activation state
  other than UISceneActivationStateForegroundActive, which is not allowed.
  （层状态=渲染中，音频会话=Playback/独占）

【从这行字里读出来的】
  · 「层状态=渲染中」说明我们的层确实挂在窗口里、正在渲染
    —— 它所在的场景本来就是前台活跃的
  · 但系统抱怨的是 **content source 的** UIScene，不是「层在不在屏幕上」
  → 也就是说，AVKit 记下的是 **content source 被创建那一刻** 的场景关联。
    我们原来是在 App 一启动就把它建好的 —— 那时层还没进任何窗口、窗口也还不是 key，
    那次关联从一开始就不合法；后来层进了窗口也纠正不回来了。

【这一版怎么改的】
  · 改成「用户点开关的那一刻才创建」content source 和控制器。
    那时层早就挂在窗口上（层状态=渲染中就是证据），App 也在前台活跃。
  · 启动梯子到第 3 级时，把控制器和 content source 整个丢掉重建一次 ——
    万一系统还记着旧关联，这是我们唯一能纠正它的机会
  · 顺手把「我们这一侧读到的场景状态」也加进失败信息里：
    下一轮如果还失败，会显示「场景=前台活跃 / 未关联 / 后台」，
    一眼就能区分是「真的不在前台」还是「系统记的是旧关联」

【怎么测】
  1. 装好删旧版，进 App 等两秒
  2. 点「PIP 后台下载」→ 确认框点「好的」
  3. 小窗可能一两秒后才出现，别重复点
  4. 起来后：去点下载 → 切后台/锁屏 → 进度继续跳

v1.0.34 做过什么（保留备查）
────────────────────────────────────────────────────────────
画中画第三次修：先让画布层「显示出来」+ 启动梯子反复试

【进展是这样的（每次报错都往前推了一步）】
  v1.0.32：报「系统一直没就绪；层状态=失败，层报错=操作已中断」
           → 查出层被后台事件打坏（-11847），改成前台启动
  v1.0.33：报「画中画启动失败：Failed to start picture in picture.」
           → 层已经好了、possible 已经为真、真的去起了，但系统在最后一步拒绝
             （AVKitErrorDomain -1001）

【-1001 的真因】AVKit 拒绝给「不在屏幕上的层」启动画中画
  而且明确包括「刚建好、还从没显示过」的层。
  更要紧的一点：isPictureInPicturePossible 报的是**配置对不对**，
  不是**此刻能不能起** —— 所以它 true 了，start 仍可能失败。

  对照我们的实现，两条都踩了：
   1) 画布层只在「开始下载」时才第一次画帧 → 点开关那一刻，层是「从没显示过」的
   2) 旧代码「possible 为真就调一次 start」，一次失败就收工

【这一版怎么改的】
  · 开场垫一帧：App 一进来就先画一次，不让层处于「从没显示过」的状态
  · 启动梯子：10 次尝试、间隔 0.35→2.0 秒（共约 7 秒），
    **每次尝试前都先画一帧再调 start** —— 因为「什么时候算显示好了」事先不知道，
    只能反复试（这是 Apple 开发者论坛那篇实战记录给出的做法）
  · 中间失败不打扰你：爬梯子期间不弹提示，爬完再一次性说清楚
  · 失败时记录系统的**附加原因**（localizedFailureReason）——
    这个字段才是真正的诊断，很多排查文章都漏了它。若这次还失败，
    提示条会直接显示系统原话，一看就知道卡在哪。

【怎么测（顺序仍然有讲究）】
  1. 装好先删旧版。进 App 等两秒（让画布层先显示出来）
  2. 点底部「PIP 后台下载」→ 确认框点「好的」
  3. 这次留意：小窗可能在**一两秒后**才出现（梯子在试），别急着再点一次
  4. 出现后：去点下载 → 切后台/锁屏 → 进度继续跳

  还是不行的话，把那行提示发我 —— 现在它会带上系统自己的原话。

v1.0.33 做过什么（保留备查）
────────────────────────────────────────────────────────────
画中画改成「前台由你点开关启动」+ 提示条不再挡按钮

【那行诊断信息很有用，它把故障点指出来了】
  设备支持=是，层状态=失败，层报错=操作已中断，音频会话=AVAudioSessionCategoryPlayback/独占
  → 音频会话那半已经对了；坏的是画布层，错误码 -11847「操作已中断」。

【根因】后台事件会作废画布层（系统已知坑）
  App 一进后台，AVSampleBufferDisplayLayer 会被打成 failed（-11847）。
  此后往层里塞帧会被系统直接忽略 → 画中画永远「没就绪」。
  而我们原来的做法恰恰是「等进了后台才去起画中画」—— 从设计上就不可能成功。
  这就是为什么 Stay 要你先点一下、弹个确认框，然后**趁 App 还在前台**立刻开好。

【这一版怎么用】
  底部多了一条常驻的开关：
    · 点「PIP 后台下载」→ 弹确认框 → 点「好的」
      → 立刻出现画中画小窗，开关变成蓝色的「PIP 后台下载中 · 点此停用」
    · 有了这个小窗，切到别的 App、锁屏，下载都继续跑
    · 想停：点开关，或者直接关掉那个小窗

  推荐顺序：先进 App 把开关点开 → 再去点下载 → 然后随便切出去。

【这一版还做了什么】
  · 画布层自愈：一旦发现层是 failed，先复位再塞帧（不然塞进去也没人看）
  · 像素缓冲补上 IOSurface 背衬（层显示的前提）
  · 提示条不再挡住按钮：从「浮在底部的浮层」改成**占一行**（把工具栏顶上去），
    并且从机制上不接收点击 —— 不可能再吃掉你的操作
  · 提示条内容更具体：如果是 -11847，会直接告诉你「层被后台事件打断，
    请在 App 还在前台时点开关重开」

【这一版没解决 / 还是老实话】
  · 从多任务上滑杀掉 App → 画中画一起没，下载停（系统边界，要靠后台
    URLSession 才能补，还没做）
  · 开关没有记忆：重开 App 要再点一次
  · 画中画没有声音、只有进度画面，这是故意的（不播任何东西）

v1.0.32 做过什么（保留备查）
────────────────────────────────────────────────────────────
修两个问题，其实是同一个根因

【你报的两个现象】
  1) 下载的视频在 App 内播放没声音，但存到相册/文件夹后播放有声音
  2) 画中画永远起不来，报「系统一直没就绪」

【根因】全项目搜 AVAudioSession：一处都没有。
  iOS 默认的音频会话类别是 soloAmbient —— **会被侧面的静音拨片静掉**。
  相册/文件 App 设的是 playback，所以同一条视频那边有声、我们这边没声。
  也就是说：文件本身没问题（跟转码无关），是播放这一侧被静音了。

  同一个缺失还卡住了画中画：
   · WWDC 2021「What's new in AVKit」原话：做画中画要
     configure your app's audio session category for playback
   · iOS 画中画实践指南：即使视频没有音轨，也必须设成 movie playback，
     否则 App 进后台时画中画窗口打不开
  我们的画中画正好一个音轨都没有 —— 于是 isPictureInPicturePossible
  恒为 false，重试到放弃，界面就显示「系统一直没就绪」。

【改法】
  新增 app/AudioSession.swift：设 playback + moviePlayback 并激活。
  用引用计数，播放器和画中画各算一个持有者，最后一个走了才让出
  （会通知其它 App，让它们的音频恢复）。配置失败的原因会记下来。

· 装完先删旧版，再装 dist\VideoGrab-unsigned.ipa
· 验证 1：在 App 内点播放 → 应该有声音了（静音拨片开着也有声音）
· 验证 2：开始下载 → 切后台/锁屏 → 应该弹出画中画小窗
  如果还是没弹出来，界面底部会给出一串具体状态（等了多久 / 层状态 /
  音频会话现状），把那行发我。

v1.0.31 做过什么（保留备查）
────────────────────────────────────────────────────────────
局域网共享：电脑浏览器直接拿手机里的视频

【怎么用】
  1. 点工具条上的 Wi-Fi 图标 → 自动开启，界面显示一个地址，形如
        http://192.168.1.7:18080/3f9a1c07b2e4d5a6/
     点「复制地址」再粘到电脑上最省事
  2. 电脑连同一个 Wi-Fi，浏览器打开这个地址
  3. 看到文件列表（📁 / 🎬 + 文件大小）→ 点文件名即开始下载
     mp4 一般能直接在线播放；m3u8/.ts 建议下载后用播放器打开
  4. 用完回到手机点「关闭共享」

【安全怎么说（不绕弯）】
  地址末尾那串 16 位十六进制是口令，作用是挡住同一个 Wi-Fi 下
  瞎扫端口的陌生人。它不是加密 —— 拿到这个地址的人都能下载，
  所以用完记得关。关掉后地址立刻失效，下次开启会换一个新口令。
  手机自己的播放走本机地址，不需要口令，完全不受影响。

【顺手做的一件事】
  共享期间切后台 / 锁屏，会自动弹画中画小窗保活（复用上一版那套）。
  不加这个的话，手机一锁屏，电脑那边下到一半就断了。

【可能会卡住的地方】
  · 手机必须连 Wi-Fi（只有蜂窝网时不对局域网开放）
  · iOS 第一次可能问「是否允许访问本地网络」，要选允许；选错了电脑打不开，
    界面里给了「打开系统设置」按钮可以过去改
  · 电脑打不开先自查：是不是同一个 Wi-Fi / 地址里口令那一段是不是漏了

【这一版没做什么（说清楚边界）】
  · 不是 WebDAV —— 电脑上不能改/删手机里的文件，只能看和下载
  · 地址是 http 不是 https，口令是明文传的（局域网内够用）
  · 换 Wi-Fi 后地址会变，要重新复制一次

【装机后怎么验这一版】
  1. 手机连 Wi-Fi → 点 Wi-Fi 图标 → 地址出现（如果显示「没找到局域网地址」
     就是手机没连 Wi-Fi）
  2. 电脑浏览器打开那个地址 → 应该看到文件列表（不是空白页、不是 403）
  3. 随手点一个 mp4 → 电脑上开始下载，速度看家里 Wi-Fi
  4. 手机按锁屏 / 切后台 → 出现画中画小窗，电脑那边下载不断 →
     说明保活生效
  5. 回到 App 点「关闭共享」→ 电脑刷新那个地址应该变成一张「需要访问口令」的页

  第 4 步如果断了，把手机界面底部显示的原因发我（画中画那行会写原因）。
  第 2 步如果是 403，多半是地址里口令那一段漏了。

v1.0.29 做过什么（保留备查）
────────────────────────────────────────────────────────────
后台保活：画中画进度窗（Stay 用的就是这一招）

以前：切后台下载就停，得盯着屏幕看进度。
现在：切后台会弹出一个小画中画窗口，里面是下载进度（任务名 / 百分比 /
      进度条 / 当前阶段），进程继续跑，下载和转码都不会停。

原理：不做任何视频播放，而是自己把进度画成画面塞进画中画的渲染管道，
      iOS 把它当成「正在播放的媒体」，于是继续给运行时间。
      这比「放一段无声音频骗系统」干净 —— 那招会被静音检测杀掉。

怎么用：正常点下载 → 直接切后台 / 锁屏 → 会出现画中画小窗。
       回前台它自动收起。
       画中画上那个播放/暂停按钮没用（下载没法暂停），忽略即可。

出问题时：界面底部会显示画中画起不来的具体原因（不静默失败）。

一个说明：从多任务里上滑「杀掉」App，画中画也会一起没 —— 这是系统边界，
         下一版会用后台传输通道（URLSession 后台会话）补上这一层。

v1.0.28 做过什么（保留备查）
────────────────────────────────────────────────────────────
请求头注入 + AES 解密补完（五家 AI 会诊里排前两位的两件事）

① 头注入：嗅探时把「页面 Referer / UA / Cookie」一起抓下来，
   下载分片和取 AES key 时都带上。之前是裸请求 + 猜的 Referer，
   碰到防盗链站只能 403。现在用真实值。

② AES 解密：原来就有实现，这次补了两处 + 修了一个真 bug
   · key 只拉一次（原来 694 个分片会重复拉 694 次）
   · IV 兜底改成「媒体序号 + 分片下标」（规范如此）
   · 修掉解析器里的单值 IV 兜底 —— 那个 IV 只对第 0 个分片正确，
     其余全错（加密源会花屏）。这个 bug 是编译器报错时顺带查出来的。
   · 解密逻辑已用公开的 AES-128 测试流在本机实测通过

这一版 = 换引擎
────────────────────────────────────────────────────────────

你的实测给出了决定性证据：同一个 .ts，别的转码软件几秒转完
（有声有画面）→ 下载和拼接完全没问题，问题全在我手写的
重封装器上。

所以这版不再自己写 —— 直接内嵌 FFmpeg 引擎（Stay、亚瑟、
各类下载器 App 内部用的同款引擎），转码改用：

    ffmpeg -i 输入.ts -c copy -movflags +faststart 输出.mp4

`-c copy` = 只换容器不重编码：
  · 秒级完成
  · 音轨原样保留（ADTS/B帧/LATM/HEVC 全由 FFmpeg 处理，
    覆盖面比我手写的解析器大几个数量级）
  · +faststart 把索引挪到文件头 → 拖进度条秒响应
  · 完成后自动体检输出文件，过程记录写明：视频轨 ✓/✗、
    音轨 ✓/✗（含采样率声道数）、时长

代价：IPA 从 0.4MB 涨到 9.2MB（FFmpeg 引擎的体积）。
