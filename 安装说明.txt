构建    2026-09-26  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.89 = 下载专项：**修掉 5 处实锤的问题**（含"重试不续传""一直显示失败"）
          + 装上一套**诊断埋点**，把"卡死/闪退"变成能查证的事

────────────────────────────────────────────────────────────
一、修掉的（每一处都在代码里核对过，附位置）
────────────────────────────────────────────────────────────
 **1. 重试能续传了（以前必从头重下）**
  原来下载分片是"边拼边删"——拼完一个分片就删一个，最后连临时目录一起删。
  **结果：一旦崩在"拼接之后 / 转码途中"（正是最容易崩的环节），续传的底料已经被
  程序自己删光了** → 你点「重试」只能从零重下。
  现在：分片留到「整条流程（含转码）成功」之后才清。

  ★ **代价（必须告诉你）**：峰值磁盘占用约 **2 倍**（分片和成品同时存在）。
    例如下 1GB 的片子，最高时约占 2GB。
    换来的是"崩了重试 = 重新拼接十几秒"，而不是"重下一遍"。
    你要是嫌占空间，这个我一行就能关掉，说一声。

 **2. 不再一直挂着红字"下载失败"**
  成功那一段漏了一句"清掉失败标记"，而列表的红字判据正是"有失败标记"——
  所以成功了也可能显红。

 **3. 崩溃/被杀后台之后重启，不再谎报失败**
  以前只要"上次没下完"，重启后就会顶着一条假的"上次运行中被中断（没下完）"红字。
  现在改成「已中断（分片还在，可直接继续）」，按钮直接是「继续」。

 **4. "文件已不在"不再误报**
  以前"还没产出"会被判成"文件丢了"，说文件不在。

 **5. ffmpeg 每次转码漏一份内存（累积）**
  ffmpeg 的参数数组用完从不释放。虽然一次不多，但它**每次转码累积一份**，
  而 ffmpeg 这条路上本来就容易越跑越胖。已清理。

────────────────────────────────────────────────────────────
二、新增：诊断埋点（这是这一版最重要的东西）
────────────────────────────────────────────────────────────
 你说得对 —— 卡死和闪退是"背着一颗炸弹"。但**我读了全部相关代码，也没能只靠读代码
 就锁定闪退的根因**（内存压力 / 主线程被堵 / 引擎内部，这三条静态上都排不掉）。
 所以这一版不假装找到根因，而是**让下一次复现自己说话**：

 每次任务现在会在「过程记录」里记下：
   · **每个阶段用了多少秒**（探测 / 下载 / 拼接 / 转码）→ 卡在哪一步
   · **内存峰值** → 是不是内存压力（卡死 + 被系统杀）
   · **主线程最长失联多少毫秒** → 是不是主线程被堵（那才是"界面卡死"）

 **怎么用**：下次再卡死或闪退，进下载页打开那个任务的**过程记录**，
 把里面那几行发我/截图给我 —— 我就能直接定位，不用再来回猜。

────────────────────────────────────────────────────────────
三、已经排除的（查过，不是问题）
────────────────────────────────────────────────────────────
 · 重封装的"背压"是**对的**：它会等 writer 说"可以收了"才喂数据，队列不会无限涨。
 · 分片是**流式落盘**的（一个一个写进磁盘），不是先攒在内存里。
 · 本地播放用的那个 HTTP 服务是**分块读写**，没有把整个文件读进内存。
 · 那个服务跑在独立线程上，不占主线程。

────────────────────────────────────────────────────────────
四、请重点试这几条
────────────────────────────────────────────────────────────
 1. **下一个大点的视频**（几百 MB 以上），留意两件事：
    · 现在应该不再经常性卡死（这次修掉的 5 处里有几处就是为它）
    · 打开那个任务的**过程记录**，看看是不是多了「▶ 下载 开始 / ■ 下载 用时 …」这类行
 2. **故意中断一次**（下到一半把 App 上划杀掉）→ 重启 → 点「继续」：
    · 应该**接着下**，不是从零重来 ← 这是第 1 条修复的验证点
    · 那个任务的文字应该是「已中断（分片还在，可直接继续）」，**不是红字失败**
 3. 如果它还是卡死/闪退 —— **一定把过程记录发我**，那是这次能不能彻底修掉的关键
 4. 顺手确认：长按下载 / 播放器横屏 / 证书站照常打开 / 缩略图还在

 这一版动了 3 个文件（Downloader / DownloadJob / FFmpegConverter）。构建：run #89 一次过。

v1.0.88 = 修「证书放行的那句提示看不到」+ 让这件事**事后可查证**

────────────────────────────────────────────────────────────
一、你报的现象，查出来是什么
────────────────────────────────────────────────────────────
 你说「现在都没有选项了，没有让我仍然访问或取消的弹窗了」。
 确认后是：**页面能正常打开，只是顶部那句提示没看到，弹窗也没有。**

   · **弹窗没了是故意的** —— 你自己选的形态（页面直接开 + 顶部轻提示），
     那个"仍然访问 / 取消"弹窗正是把网页弄成打不开的元凶，所以去掉了；
   · **页面能开 = 放行成功了** ✓
   · **只有那句提示没看到 = 真缺陷** → 这一版修的就是它。

────────────────────────────────────────────────────────────
二、为什么没看到（以及怎么修的）
────────────────────────────────────────────────────────────
 那句提示原来只活 **1.8 秒** —— 而它有 18 个字，这时候页面又正好在加载，
 你的注意力在页面上，**实测就是读不完、被错过**。

 修法：
   1. 提示时长从 1.8 秒 **延长到 8 秒**（普通提示如"已复制地址"仍是 1.8 秒，没动）
   2. 提示**点一下就能收掉**（不想等它自己走就点掉）
   3. ★ **可查证**：设置里新增「**最近一次放行：<域名> · 时间**」——
      即使错过提示也不丢信息。而且这样就能分清两种情况：
        · 设置里显示「刚刚 · <域名>」→ 检测到了，只是提示没看到；
        · 什么都不显示 → 检测那一层就没走到（那就是另一个问题，得换思路查）。

────────────────────────────────────────────────────────────
三、请重点试这几条
────────────────────────────────────────────────────────────
 1. **进那个证书有问题的站** → 顶部应该出现一句提示，**停留约 8 秒**，点一下能收掉
 2. **设置 → 证书** → 应该看到「最近一次放行：<域名>」+ 时间（刚刚）
 3. **关掉 App 再打开** → 再进同一个站 → **不该再提示**（"永久记住"）
 4. 顺手确认：长按下载 / 播放器横屏 / 标签页组 / 重启标签还在 / 缩略图还在

 ★ 如果这次**第 1 条还是看不到提示**，请先看**第 2 条**：
   · 设置里有记录 → 是"提示没显示出来"，我再去查提示那条路；
   · 设置里没记录 → 是"检测没走到"，那要换思路查（不是提示的问题）。
   这样你回一句话我就能定位，不用来回猜。

 这一版只动了提示的显示与留痕，共 4 个文件。构建：run #88 一次过。

  视频抓取（VideoGrab）  v1.0.87   安装说明
════════════════════════════════════════════════════════════

文件    VideoGrab 目录根下 VideoGrab-unsigned.ipa（固定名字，每次构建自动刷新）
仓库    https://github.com/luowenbin061-blip/video-grab
构建    2026-09-26  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.87 = 修「证书提示造成无法访问网页」：**一律照常打开**，只在第一次提醒一句，
          之后永久不再提示

────────────────────────────────────────────────────────────
一、先说清这个提示到底是什么（**不是我们额外加的限制**）
────────────────────────────────────────────────────────────
 有些网站的身份证书不被系统信任（过期了、自己签的、或者身份对不上）。遇到这种站，
 **iOS 系统会拒绝连接** —— Safari、Chrome 也一样会拦，这是系统级的，不是我们加的。

 我们（这个 App）只做两件事：把系统的话翻成人话、并决定怎么处理。

 顺带排除一个可能：**我们没有"只准 https"的限制** —— 底层 http 是全开的，
 老站点也能开。

────────────────────────────────────────────────────────────
二、改成了什么样（按你提的四点要求）
────────────────────────────────────────────────────────────
 你的要求：不能影响正常访问 / 首次可以提示 / 选了仍然访问之后下次不能再提示 /
 不拦截网站加载，可以有提醒，但是去留由用户自己定。

 现在是：
   1. **页面照常打开** —— 证书有问题的站我们**一律放行**，不再拦、不再出现"打不开"；
   2. **第一次**遇到这个站 → 屏幕顶部**轻提示一句**（不挡页面、不用你点任何东西）：
      「这个网站的证书不被信任，已放行 —— 以后不再提示」
   3. 之后**永久不再提示**（名单记在磁盘上，重开 App 也记得）；
   4. 去留完全由你 —— 我们不拦任何网站，也不替你决定。

 设置里多了个出口：**设置 → 证书 →「忘掉所有已放行的网站」**（想反悔就用它；
 忘掉后下次会重新提醒一次，但页面照样放行）。

────────────────────────────────────────────────────────────
三、顺手修掉的一处误导
────────────────────────────────────────────────────────────
 系统报的错里有两种，以前被我们混成一种了：
   · **证书问题**（-1202 这类）—— 跟证书有关 ✓
   · **安全连接失败**（-1200）—— 多是"这个网站用的加密方式太老"，**跟证书无关**
 以前 -1200 也被说成"证书有问题"，还给你一个「仍然访问」按钮 ——
 **点了根本没用**，属于骗你去点一个没用的按钮。现在它单独一条，照实说清楚。

────────────────────────────────────────────────────────────
四、有一类是真的做不到的（先说清，免得你以为是 bug）
────────────────────────────────────────────────────────────
 如果网站只支持**太老的加密方式**（TLS 1.0 那种），那在**系统层面**就握不上手 ——
 **Safari 也进不去**，这一步任何 App 都没法绕过。
 这类站会看到一个明确说明（「连不上它的加密通道」），而不是含糊的"证书有问题"。

────────────────────────────────────────────────────────────
五、请重点试这几条
────────────────────────────────────────────────────────────
 1. **原来打不开的那几个站**：现在应该**直接打开**，只在第一次看到顶部一句轻提示
 2. **同一个站再进一次**：**不应该再提示**（这是"永久记住"的验证点）
 3. **关掉 App 再打开**，再进那个站 —— **仍然不提示**（这是"存盘"的验证点）
 4. 设置 → 证书 → 看「已放行的网站」数字对不对，「忘掉」之后会重新提示一次
 5. 顺手确认：长按下载 / 播放器横屏 / 标签页组 / 重启后标签还在 / 缩略图还在

 这一版新增 1 个文件（TrustedHosts.swift），改动 3 个文件。构建：run #87 一次过。

  视频抓取（VideoGrab）  v1.0.86   安装说明
════════════════════════════════════════════════════════════

文件    VideoGrab 目录根下 VideoGrab-unsigned.ipa（固定名字，每次构建自动刷新）
仓库    https://github.com/luowenbin061-blip/video-grab
构建    2026-09-26  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.86 = AI 审查第二批：**六处**（同时开着的网页不再超标／网页反复崩会认输／
          超长页面的重活会跳过／缩略图换 JPEG 省内存／长按诊断不再误导／
          恢复标签时地址坏了会说一声）

────────────────────────────────────────────────────────────
一、同时活着的网页，不再超过 3 个
────────────────────────────────────────────────────────────
 我们规定"同时最多跑 3 个网页，其余睡下"。但"让谁睡"这一步给**刚切走不到 2 秒的**
 开了豁免（为的是留时间给旧标签截图）。

 **问题**：你**快速连点切标签**的时候，每个刚看过的标签都在豁免期内 →
 **一个都不符合条件 → 一个都不睡** → 活着的一直堆，每个几十 MB。
 （三家 AI 独立提到了这条。）

 **怎么修**：不是把那 2 秒砍短（砍短了缩略图会变白），而是**盯住"截图这件事本身"**：
 正在截图的那个先不睡，**截完了立刻睡**。另外加两重兜底 —— 万一截图回调不来，
 3 秒后照样可以睡；真堆到超过上限 2 个，就直接睡最久没用的那个。

────────────────────────────────────────────────────────────
二、网页反复崩 → 会认输了
────────────────────────────────────────────────────────────
 网页的渲染进程崩掉时我们本来就会自动重载（不然是白屏、点什么都没反应）。
 但原来**没有上限** —— 遇到那种稳定把内核搞崩的页面，就是"崩 → 重载 → 崩"死循环，
 风扇起飞、电量狂掉。

 现在崩够 **3 次**就停手，给你一整页说明（"这个网页一直崩"），
 要不要再来由你决定 —— 点「重试」会给一次全新的机会。
 （Safari 也是自动重载、崩几次就放弃，这里对齐它。）

────────────────────────────────────────────────────────────
三、超长页面的"重活"会跳过了
────────────────────────────────────────────────────────────
 嗅探里最贵的一步是"把整页 HTML 序列化再跑正则"（找藏在源码里的视频地址）。
 这一步是**同步**的，中途打不断 —— 所以只能"做之前先看成本，太大就直接放弃"。

 现在这个页面如果有 **4 万个以上元素**，这步直接跳过（30 秒内不再试）；
 万一还是慢了（真的花了 300 毫秒以上），再自动冷一会儿。
 代价是"超复杂页面可能少嗅探到几条"，换来的是**页面不会卡住**。

────────────────────────────────────────────────────────────
四、缩略图从 PNG 换成 JPEG（省内存）
────────────────────────────────────────────────────────────
 网页截图是连续色调的图，PNG（无损）在这种内容上效率极差 ——
 实测 15 张 7.5 MB，换 JPEG 大约 1 MB。

 **★ 老图会迁移**：你以前的缩略图**一张都不会丢** —— 读到旧的就顺手转成新格式。

────────────────────────────────────────────────────────────
五、长按诊断里的一句谎话修掉了
────────────────────────────────────────────────────────────
 开着长按诊断时，如果点到的是 iframe，以前一律写"跨域进不去"。
 但"同源 iframe 还没加载完"其实也拿不到内容 —— 于是被一起报成了"跨域"，
 **照着"跨域"去查是白查**。

 现在按真实原因分开说：真跨域就是跨域；同源拿不到内容 = 还没加载完。

────────────────────────────────────────────────────────────
六、恢复标签时地址是坏的，会说一声
────────────────────────────────────────────────────────────
 上一版（v1.0.84）修了"地址栏手输非法地址"那条路，但**恢复标签**那条路漏了 ——
 存档里的地址解析不出来时，以前什么都不做：标签白着、也不说为什么。
 现在会提示一句，并把它恢复成空白标签。

────────────────────────────────────────────────────────────
请重点试这几条
────────────────────────────────────────────────────────────
 1. **快速连点切标签**（④条里最值得试的）：开 4~5 个标签来回快点切，
    切完回到某个标签，**页面应该还在、不是白的**（白 = 被睡错了）
 2. **缩略图**：升级后打开标签网格，**老标签的缩略图应该还在**（这是迁移的验证点；
    要是全白了/空了，说明迁移没生效，告诉我）
 3. 上限/崩溃认输/重活保护这三条**触发条件比较少见**，日常用不出来是正常的 ——
    不用特意去构造，留意即可
 4. 顺手确认：长按下载、播放器横屏、标签页组、重启后标签还在，都正常

 这一版动了 5 个文件（4 个 Swift + 1 个注入脚本）。
 构建：run #86 一次过。

  视频抓取（VideoGrab）  v1.0.85   安装说明

文件    VideoGrab 目录根下 VideoGrab-unsigned.ipa（固定名字，每次构建自动刷新）
仓库    https://github.com/luowenbin061-blip/video-grab
构建    2026-09-26  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.85 = AI 审查第一批：**四条**（存档不再「坏了就全丢」／下不了的视频不再骗你说
          "成功"／嗅探列表封顶／来电・拔耳机后音频有反应）

────────────────────────────────────────────────────────────
一、存档读坏了，标签不再"一次性全没"
────────────────────────────────────────────────────────────
 以前读存档只要是失败（文件损坏、或格式对不上），就当"没有存档"处理 ——
 **标签全没，而且不告诉你为什么。** 更麻烦的是这是以后的雷：
 只要以后给存档加一个新字段，老用户的标签就会**一次性全丢**。

 现在：
   · 单个字段读不出来 → 只用**那一个**的默认值，**别的照旧读回来**（加字段不再掀桌）
   · 真的整份读不了 → 明确提示「上次的标签没能恢复：<原因>」，**不再闷着**
   · 存盘失败也会留痕（以前存失败一声不响，你以为存上了）

────────────────────────────────────────────────────────────
二、下不了的视频，不再"骗你说下载成功"
────────────────────────────────────────────────────────────
 有一类网站的 HLS 视频，清单第一行会指向一个「开头文件」（fMP4 格式，业内叫
 #EXT-X-MAP）。**以前这行我们不认，直接跳过** → 把后面的分片硬拼起来 →
 **得到一个缺了开头、根本打不开的文件，界面上却显示「下载成功」。**

   · 另外还有一份**弱引用副本**，专门给「前往 / 刷新 / 后退」这些按钮用

          + 证书有问题的网站给「仍然访问」；顺手删掉页面顶部那个挡内容的转圈

────────────────────────────────────────────────────────────
一、网页里的弹窗：原来一个都不显示
────────────────────────────────────────────────────────────
 网页里的 alert（提示）、confirm（问你要不要继续）、prompt（让你输个字），
 我们原来**三个回调一个都没实现**。后果是这样的：

   不实现时，WebKit 自己当「确定 / 取消」处理 —— 所以**页面不会卡**，
   但你**什么都看不见**。有些网站靠它提示信息、或者问「要不要继续」，
   在我们这儿就表现成「点了没反应」，看着就像坏了。

 现在：网页一弹，就用**系统自己的弹窗**显示出来（跟 Safari 长得一样），
 标题显示网站域名，你点完再把结果告诉网页。

 ★ 最要命的一条（写代码时专门盯住的）：**必须把「你点了什么」回报给网页**。
   忘了回报，网页的 JS 引擎会一直等着它 —— 表现就是**页面卡死**。
   所以每条路径都过一道「只允许回报一次」的闸，连「弹窗没弹出来」这种情况
   也必须回报（按默认答案），绝不让网页干等。

 几个细节：
   · 只有你**正在看的那一页**才弹 —— 后台窗口突然弹个框出来只会让人莫名其妙。
   · 同一时刻只允许一个系统弹窗（有的网站会连环弹，全堆上来就乱了）。

────────────────────────────────────────────────────────────
二、打不开的时候：整页告诉你为什么
────────────────────────────────────────────────────────────
 原来加载失败只在屏幕上闪一行小字，1.8 秒就没了 —— 你根本来不及看清
 是「没网」还是「地址错了」还是「证书有问题」。现在照 Safari 的做法，**整页盖住**：

   图标 + 一句人话（比如「没有网络」）+ 能做什么 + 「重试」按钮
   最下面小字给出错地址和错误码（平时不用看，出问题时报我一句就能定位）

 常见的几种翻法：
   连不上网        → 没有网络：看一眼 Wi-Fi 或流量是不是断了
   域名找不到      → 找不到这个网站：地址可能拼错了，也可能它已经不存在了
   服务器拒绝连接  → 连不上这个网站：它可能挂了，也可能被当前网络屏蔽了
   等太久没回话    → 网站没反应：可能网络慢，也可能它本身有问题
   证书不受信任    → 这个网站的证书有问题（见第三条）

 ★ 有一个坑必须堵住，不然会很莫名其妙：**你自己点「停止」、或者页面自己跳转时，
   系统也会报一次「加载失败」**（它报的是「已取消」）。这两个我已经滤掉了 ——
   不然会出现「我点了个链接，反而弹出一个错误页」。
   另一类是超时兜底（25 秒没加载完）也走同一个错误页。

 另外：后台窗口加载失败**不会**打扰你，但原因记在它自己的标签里，切过去能看到。

────────────────────────────────────────────────────────────
一、★「长时间不点击就卡死」的元凶：是我们自己注入的嗅探脚本
────────────────────────────────────────────────────────────
 你答「卡死时页面还在、能滚动，但按钮点不动」—— 这一条很关键：
 滚动能用说明**合成线程正常**，点击没反应说明**页面的 JS 主线程被堵住了**。
 顺着这条线查注入脚本，找到两处：

 ① **每 3 秒把"资源加载记录"整个遍历一遍**
    performance.getEntriesByType('resource') 返回的是**这一页从打开到现在所有**的资源记录，
    那个数组只会越来越长 —— 所以每 3 秒全量走一遍，是**越用越慢**的。
    而旁边**早就有一个 PerformanceObserver** 在干同一件事（事件驱动、只推新增的）——
    典型的新机制加了、旧的忘了删。→ **把那个全量轮询整个删掉。**
 ② **页面里一有 DOM 变化，就全文档重扫一遍**
    弹幕、计时器、广告轮播这类页面每秒都在改 DOM → 一直在重扫。
    → 改成先做一次极便宜的判断：**这次变化里有没有新增的视频元素**（没有就什么都不做），
      有也只在那棵新子树里查，不再全文档扫。
 ③ 另加一道自保：单次扫描超过 60 毫秒就自动歇 4 轮 —— **宁可少嗅探，也绝不堵页面。**

 这三条上去，"用久了卡、点了没反应"应该明显好转（这是这批里最值钱的修复）。

────────────────────────────────────────────────────────────
二、「顶部网址固定不变」的真根因
────────────────────────────────────────────────────────────
 不是"更新得慢"，是**真的固定了**：地址栏绑的是界面自己的一个变量，
 而它只在页面**第一次出现时**从真实地址同步过一次 —— 之后就再也没人更新它。
 再加上真实地址本身也只在"页面完全加载完"那一刻才更新（点站内链接换页、换 hash 都不触发），
 两个原因叠在一起。改：
 · 地址一变就跟着更新到地址栏；**你正在地址栏里打字时不会被覆盖**（按焦点判断）。
 · 真实地址改成三路驱动：浏览器自己报的地址变化（**含站内路由、换 hash**）、
   内容一开始到达、以及加载完成 —— 对齐 Safari：**地址先变，页面慢慢来**。

────────────────────────────────────────────────────────────
三、新增：加载进度条 / 停止键 / 崩溃恢复 / 超时兜底
────────────────────────────────────────────────────────────
 · **加载进度条**：贴在地址栏**正下方**一根细线（跟 Safari 同位置），随真实进度推进，
   走满后收起。
 · **停止键**：加载中底部那一格变成 ✕（跟 Safari 一样），点一下停下并复位。
 · **崩溃自动恢复**：网页的渲染进程被系统回收时（内存紧张时常见），
   原来就是白屏/冻住、只能手动刷新；现在提示一句并**自动重载**。
 · **加载超时兜底**：加载开始 25 秒还没完成 → 复位状态并提示"可以点刷新重试"。
   原来这种情况下状态会一直停在"加载中"，界面看着就像死了。

────────────────────────────────────────────────────────────
四、浏览器摸底结论（对标 Safari，扫了 25 个能力点）
────────────────────────────────────────────────────────────
 **这批已修**：进度条、地址实时跟随、进程崩溃恢复、加载超时/停止、
 再加上上面那个自己造成的性能问题。

 **下一批要做的（你已经确认）**：
   · **网页弹窗**（alert / confirm / 输入框）—— 三个回调我们现在**一个都没实现**，

 **竖屏一个字没动**（你说 OK 的那组：距右 113 / 距下 53）。

────────────────────────────────────────────────────────────
 量的结果：左上 ✕ 视觉 15pt、小窗图标 20pt、我们的箭头 19.5pt

三、右滑时"一闪一闪"：根因在我这边（你确认系统控制条是稳的，这条证据很关键）
────────────────────────────────────────────────────────────
 根因：**手指一按下去，系统可能正把控制条点亮**（左右滑动调进度就是这种情况），

 · **手指一按就冻结**：这段时间显隐只听我们自己的，不看系统读数（你说不要显示就不显示）
 · **松手后 0.25 秒才解冻**：躲开系统在松手瞬间的状态抖动；之后由系统读数接管

 · **删掉"拖进度条松手立刻恢复"那个特例**（你确认过）：拖进度条时系统控制条本来就
   是显示的，解冻后 ≤100ms 我们自动跟着亮 —— 效果一样，但不用再猜"手指起点在不在
   进度条上"。那个猜法正是右滑被误判、进而闪的来源。
 · 点击仍**立即响应**（本地先切，0.25 秒后交回系统读数确认）

文件    dist\VideoGrab-unsigned.ipa   （9.5 MB）
仓库    https://github.com/luowenbin061-blip/video-grab
构建    2026-09-24  GitHub Actions / macos-14 / Xcode 15.4
适用    iOS 15.0 以上（你的 16.6 没问题）

v1.0.51（= WebDAV 第二档：手机变成电脑上的一个盘）

【以前什么样】
 同一 Wi-Fi 下电脑浏览器打开地址，能看到文件列表、点着下载 ——
 但只能看和拿，像隔着窗户看东西。

【现在什么样】
 手机能挂成电脑上的一个「网络磁盘」：出现在「此电脑」里，
 能拖文件进出、改名、删除，双击就用电脑自己的播放器播。

【电脑上怎么连 —— 两种办法，选一个】

 办法一（推荐，最省事）：装个 WebDAV 客户端
   · Windows：RaiDrive（免费版够用）或 Cyberduck
   · 填这三样（App 的共享页里都有，可一键复制）：
       地址 = http://192.168.x.x:18080/
       用户名 = 随便填
       密码 = 那串口令

 办法二：用 Windows 自带的「映射网络驱动器」—— 要多做一步
   Windows 默认只肯连 https 的 WebDAV，http 地址必须先改注册表：
     1) 开始菜单搜 regedit 打开
     2) 找到 HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\WebClient\Parameters
     3) 把 BasicAuthLevel 改成 2（没有这个值就新建一个 DWORD 32 位）
     4) 顺手把 FileSizeLimitInBytes 改成 4294967295（不然大文件传不动）
     5) 重启电脑（或者只重启 WebClient 服务）
   然后再用「此电脑 → 映射网络驱动器」填上面那个地址。
   ★ 这一步改的是系统设置；不想改就用办法一。

【安全提醒（重要，请看完）】
 · 只在家里的 Wi-Fi 用。口令是门牌、不是加密 —— 别在公共 Wi-Fi 开着共享。
 · 拿到地址和口令的人**能改删你的文件**。用完点「关闭共享」：地址立刻失效，
   下次开启会换一个新口令。
 · 根目录不给删（防手滑）；单个文件上传限 500MB。

【装上后重点看这几条】
 1. 共享页里是不是多了一栏「挂成电脑上的一个盘（WebDAV）」，地址和口令都能复制
 2. 电脑上按办法一填好 → 手机能不能出现在「此电脑」里
 3. 能不能把电脑里的文件拖进手机（或右键上传）
 4. 能不能改名、删掉一个文件
 5. 原来的浏览器方式（点文件名下载）是不是照旧好用

【需求 2 · 页面加载慢 / 滑动不跟手 —— 原因查出来了，是注入脚本】
  sniffer.js 里有两处硬伤，都压在热路径上：
   · 每轮扫描都把**整页 HTML 序列化成字符串**（几百 KB ~ 几 MB）再跑正则，
     而它挂在「每 1.5 秒」的定时器上；
   · DOM 监听没有节流 —— 页面每变一次 DOM 就跑上面那一整套，
     现代网页一秒能变几十次。
  两处叠加 = 每秒几十次全页序列化。这不是 WKWebView 天生慢。

  改法（按代价分三层）：
   · 轻活（媒体元素 + 页面全局变量）→ 定时器（1.5 秒 → 3 秒）和 DOM 变化照跑，
     且 DOM 变化合并 400ms 内的多次变动，只跑一次
   · 重活（整页序列化 + 正则）→ 只在页面加载完成后、你手动刷新/长按时各跑一次
   · 首扫从「脚本一注入就扫」推到 DOM 建好之后（原来那次 DOM 还是空的，纯白跑）
   · 上报加 500ms 最小间隔（原生每收一次都要重排整个列表）
   · 补上 src 属性监听 —— 有些播放器用 setAttribute 写地址，
     原来靠 1.5 秒定时器的全量扫兜着，现在显式补上（不丢能力）

  顺带一个实测发现（也是本批唯一被自己推翻的东西）：
  我一开始还加了「先用 indexOf 预筛、没有扩展名就跳过正则」，理由是「省一次正则」。
  实测五个真实页面：全量正则平均 0.11 ms，预筛 0.206 ms —— 预筛要扫 6 遍、正则只扫 1 遍，
  加它净亏。所以撤掉了。注释里留了数据，免得以后又被「看起来能省一点」的直觉带回去。

  WebView 那边配置本来就是齐的，唯一能改的是**预热**：App 一启动就先加载一次空白页，
  让 WebKit 提前把网页进程拉起来 —— 你第一次真正打开网页时就不用等这套冷启动。
  （Safari 的进程一直是热的，这是它在首屏上快的原因之一，也是我们能自己消掉的一段。）

【五家 AI 的会诊结果：三条实质答案，两条结论独立撞在一起】

◆ 结论一（两家分别独立得出，说法几乎一样）：
  真正的病灶不是「场景类型」，而是 **承载画面的那个视图根本没进到前台活跃的窗口里**。
  原话：「你用 UIViewRepresentable 的 .background 挂一个 3×3 的视图，
  makeUIView 返回时 view.window == nil，content source 关联到一个无窗口的层，
  AVKit 记下的场景关联从一开始就不合法 —— **懒创建或重建都没用**，
  因为重建时机同样早于 didMoveToWindow；而且 3×3 不满足『inline 视图非零』的隐含要求。」

  → 这一版：不再让 SwiftUI 承载那个视图，改成 App 自己把宿主视图（180×101，明确非零）
    加到 keyWindow 的**最底层**（被上面不透明的页面盖住，你看不见它）；
    要建控制器之前，先确认层真的已经在窗口里，不满足就等，不浪费尝试次数。

◆ 结论二（第三家）：
  「送帧必须走固定节奏，而且**与启动重试各走各的**。你那个梯子间隔最长到 2 秒，
  等于在饿着层；层长时间收不到帧会自己进 failed（-11847），层一旦 failed，
  后面重试多少次 start 都不会成功 —— 这就是『重试 10 次全失败』的一个很可能的原因。」

  → 这一版：送帧改成**每 0.35 秒一帧**的固定节奏，在点开关时就开（不再等小窗起来才开），
    并且挂在 RunLoop 的 common 模式上（滚动页面时也不断）。

◆ 结论三（判断后决定不换路）：
  视频通话那套（AVPictureInPictureVideoCallViewController）**不能绕过这个错误** ——
  两条路都要求 start 那一刻场景是前台活跃。而 Stay 用的正是我们这条路
  （它要完全控制帧的时序和分辨率）。所以继续走这条路，不折腾。

【这一版其它小改动】
  · 第一级启动延后 0.6 秒（不贴着确认框关闭那一瞬间调）
  · 每级尝试前先确认场景是前台活跃，不在就等（不消耗尝试次数）
  · 重试从 10 次拉到 12 次（约 10 秒），中途整个重建一次
  · 还是不行的话，报错会带上：层状态 / 场景状态 / 音频会话 / 系统原话

画中画第四次修：content source 改成「用的时候才建」

【你的报错终于把真话说全了】
  AVKitErrorDomain -1001: Failed to start picture in picture. /
  The UIScene for the content source has an activation state
  other than UISceneActivationStateForegroundActive, which is not allowed.
  （层状态=渲染中，音频会话=Playback/独占）

【从这行字里读出来的】
  · 「层状态=渲染中」说明我们的层确实挂在窗口里、正在渲染
    —— 它所在的场景本来就是前台活跃的
  · 但系统抱怨的是 **content source 的** UIScene，不是「层在不在屏幕上」
  → 也就是说，AVKit 记下的是 **content source 被创建那一刻** 的场景关联。
    我们原来是在 App 一启动就把它建好的 —— 那时层还没进任何窗口、窗口也还不是 key，
    那次关联从一开始就不合法；后来层进了窗口也纠正不回来了。

【这一版怎么改的】
  · 改成「用户点开关的那一刻才创建」content source 和控制器。
    那时层早就挂在窗口上（层状态=渲染中就是证据），App 也在前台活跃。
  · 启动梯子到第 3 级时，把控制器和 content source 整个丢掉重建一次 ——
    万一系统还记着旧关联，这是我们唯一能纠正它的机会
  · 顺手把「我们这一侧读到的场景状态」也加进失败信息里：
    下一轮如果还失败，会显示「场景=前台活跃 / 未关联 / 后台」，
    一眼就能区分是「真的不在前台」还是「系统记的是旧关联」

【怎么测】
  1. 装好删旧版，进 App 等两秒
  2. 点「PIP 后台下载」→ 确认框点「好的」
  3. 小窗可能一两秒后才出现，别重复点
  4. 起来后：去点下载 → 切后台/锁屏 → 进度继续跳

v1.0.34 做过什么（保留备查）
────────────────────────────────────────────────────────────
画中画第三次修：先让画布层「显示出来」+ 启动梯子反复试

【进展是这样的（每次报错都往前推了一步）】
  v1.0.32：报「系统一直没就绪；层状态=失败，层报错=操作已中断」
           → 查出层被后台事件打坏（-11847），改成前台启动
  v1.0.33：报「画中画启动失败：Failed to start picture in picture.」
           → 层已经好了、possible 已经为真、真的去起了，但系统在最后一步拒绝
             （AVKitErrorDomain -1001）

【-1001 的真因】AVKit 拒绝给「不在屏幕上的层」启动画中画
  而且明确包括「刚建好、还从没显示过」的层。
  更要紧的一点：isPictureInPicturePossible 报的是**配置对不对**，
  不是**此刻能不能起** —— 所以它 true 了，start 仍可能失败。

  对照我们的实现，两条都踩了：
   1) 画布层只在「开始下载」时才第一次画帧 → 点开关那一刻，层是「从没显示过」的
   2) 旧代码「possible 为真就调一次 start」，一次失败就收工

【这一版怎么改的】
  · 开场垫一帧：App 一进来就先画一次，不让层处于「从没显示过」的状态
  · 启动梯子：10 次尝试、间隔 0.35→2.0 秒（共约 7 秒），
    **每次尝试前都先画一帧再调 start** —— 因为「什么时候算显示好了」事先不知道，
    只能反复试（这是 Apple 开发者论坛那篇实战记录给出的做法）
  · 中间失败不打扰你：爬梯子期间不弹提示，爬完再一次性说清楚
  · 失败时记录系统的**附加原因**（localizedFailureReason）——
    这个字段才是真正的诊断，很多排查文章都漏了它。若这次还失败，
    提示条会直接显示系统原话，一看就知道卡在哪。

【怎么测（顺序仍然有讲究）】
  1. 装好先删旧版。进 App 等两秒（让画布层先显示出来）
  2. 点底部「PIP 后台下载」→ 确认框点「好的」
  3. 这次留意：小窗可能在**一两秒后**才出现（梯子在试），别急着再点一次
  4. 出现后：去点下载 → 切后台/锁屏 → 进度继续跳

  还是不行的话，把那行提示发我 —— 现在它会带上系统自己的原话。

v1.0.33 做过什么（保留备查）
────────────────────────────────────────────────────────────
画中画改成「前台由你点开关启动」+ 提示条不再挡按钮

【那行诊断信息很有用，它把故障点指出来了】
  设备支持=是，层状态=失败，层报错=操作已中断，音频会话=AVAudioSessionCategoryPlayback/独占
  → 音频会话那半已经对了；坏的是画布层，错误码 -11847「操作已中断」。

【根因】后台事件会作废画布层（系统已知坑）
  App 一进后台，AVSampleBufferDisplayLayer 会被打成 failed（-11847）。
  此后往层里塞帧会被系统直接忽略 → 画中画永远「没就绪」。
  而我们原来的做法恰恰是「等进了后台才去起画中画」—— 从设计上就不可能成功。
  这就是为什么 Stay 要你先点一下、弹个确认框，然后**趁 App 还在前台**立刻开好。

【这一版怎么用】
  底部多了一条常驻的开关：
    · 点「PIP 后台下载」→ 弹确认框 → 点「好的」
      → 立刻出现画中画小窗，开关变成蓝色的「PIP 后台下载中 · 点此停用」
    · 有了这个小窗，切到别的 App、锁屏，下载都继续跑
    · 想停：点开关，或者直接关掉那个小窗

  推荐顺序：先进 App 把开关点开 → 再去点下载 → 然后随便切出去。

【这一版还做了什么】
  · 画布层自愈：一旦发现层是 failed，先复位再塞帧（不然塞进去也没人看）
  · 像素缓冲补上 IOSurface 背衬（层显示的前提）
  · 提示条不再挡住按钮：从「浮在底部的浮层」改成**占一行**（把工具栏顶上去），
    并且从机制上不接收点击 —— 不可能再吃掉你的操作
  · 提示条内容更具体：如果是 -11847，会直接告诉你「层被后台事件打断，
    请在 App 还在前台时点开关重开」

【这一版没解决 / 还是老实话】
  · 从多任务上滑杀掉 App → 画中画一起没，下载停（系统边界，要靠后台
    URLSession 才能补，还没做）
  · 开关没有记忆：重开 App 要再点一次
  · 画中画没有声音、只有进度画面，这是故意的（不播任何东西）

v1.0.32 做过什么（保留备查）
────────────────────────────────────────────────────────────
修两个问题，其实是同一个根因

【你报的两个现象】
  1) 下载的视频在 App 内播放没声音，但存到相册/文件夹后播放有声音
  2) 画中画永远起不来，报「系统一直没就绪」

【根因】全项目搜 AVAudioSession：一处都没有。
  iOS 默认的音频会话类别是 soloAmbient —— **会被侧面的静音拨片静掉**。
  相册/文件 App 设的是 playback，所以同一条视频那边有声、我们这边没声。
  也就是说：文件本身没问题（跟转码无关），是播放这一侧被静音了。

  同一个缺失还卡住了画中画：
   · WWDC 2021「What's new in AVKit」原话：做画中画要
     configure your app's audio session category for playback
   · iOS 画中画实践指南：即使视频没有音轨，也必须设成 movie playback，
     否则 App 进后台时画中画窗口打不开
  我们的画中画正好一个音轨都没有 —— 于是 isPictureInPicturePossible
  恒为 false，重试到放弃，界面就显示「系统一直没就绪」。

【改法】
  新增 app/AudioSession.swift：设 playback + moviePlayback 并激活。
  用引用计数，播放器和画中画各算一个持有者，最后一个走了才让出
  （会通知其它 App，让它们的音频恢复）。配置失败的原因会记下来。

· 装完先删旧版，再装 dist\VideoGrab-unsigned.ipa
· 验证 1：在 App 内点播放 → 应该有声音了（静音拨片开着也有声音）
· 验证 2：开始下载 → 切后台/锁屏 → 应该弹出画中画小窗
  如果还是没弹出来，界面底部会给出一串具体状态（等了多久 / 层状态 /
  音频会话现状），把那行发我。

v1.0.31 做过什么（保留备查）
────────────────────────────────────────────────────────────
局域网共享：电脑浏览器直接拿手机里的视频

【怎么用】
  1. 点工具条上的 Wi-Fi 图标 → 自动开启，界面显示一个地址，形如
        http://192.168.1.7:18080/3f9a1c07b2e4d5a6/
     点「复制地址」再粘到电脑上最省事
  2. 电脑连同一个 Wi-Fi，浏览器打开这个地址
  3. 看到文件列表（📁 / 🎬 + 文件大小）→ 点文件名即开始下载
     mp4 一般能直接在线播放；m3u8/.ts 建议下载后用播放器打开
  4. 用完回到手机点「关闭共享」

【安全怎么说（不绕弯）】
  地址末尾那串 16 位十六进制是口令，作用是挡住同一个 Wi-Fi 下
  瞎扫端口的陌生人。它不是加密 —— 拿到这个地址的人都能下载，
  所以用完记得关。关掉后地址立刻失效，下次开启会换一个新口令。
  手机自己的播放走本机地址，不需要口令，完全不受影响。

【顺手做的一件事】
  共享期间切后台 / 锁屏，会自动弹画中画小窗保活（复用上一版那套）。
  不加这个的话，手机一锁屏，电脑那边下到一半就断了。

【可能会卡住的地方】
  · 手机必须连 Wi-Fi（只有蜂窝网时不对局域网开放）
  · iOS 第一次可能问「是否允许访问本地网络」，要选允许；选错了电脑打不开，
    界面里给了「打开系统设置」按钮可以过去改
  · 电脑打不开先自查：是不是同一个 Wi-Fi / 地址里口令那一段是不是漏了

【这一版没做什么（说清楚边界）】
  · 不是 WebDAV —— 电脑上不能改/删手机里的文件，只能看和下载
  · 地址是 http 不是 https，口令是明文传的（局域网内够用）
  · 换 Wi-Fi 后地址会变，要重新复制一次

【装机后怎么验这一版】
  1. 手机连 Wi-Fi → 点 Wi-Fi 图标 → 地址出现（如果显示「没找到局域网地址」
     就是手机没连 Wi-Fi）
  2. 电脑浏览器打开那个地址 → 应该看到文件列表（不是空白页、不是 403）
  3. 随手点一个 mp4 → 电脑上开始下载，速度看家里 Wi-Fi
  4. 手机按锁屏 / 切后台 → 出现画中画小窗，电脑那边下载不断 →
     说明保活生效
  5. 回到 App 点「关闭共享」→ 电脑刷新那个地址应该变成一张「需要访问口令」的页

  第 4 步如果断了，把手机界面底部显示的原因发我（画中画那行会写原因）。
  第 2 步如果是 403，多半是地址里口令那一段漏了。

v1.0.29 做过什么（保留备查）
────────────────────────────────────────────────────────────
后台保活：画中画进度窗（Stay 用的就是这一招）

以前：切后台下载就停，得盯着屏幕看进度。
现在：切后台会弹出一个小画中画窗口，里面是下载进度（任务名 / 百分比 /
      进度条 / 当前阶段），进程继续跑，下载和转码都不会停。

原理：不做任何视频播放，而是自己把进度画成画面塞进画中画的渲染管道，
      iOS 把它当成「正在播放的媒体」，于是继续给运行时间。
      这比「放一段无声音频骗系统」干净 —— 那招会被静音检测杀掉。

怎么用：正常点下载 → 直接切后台 / 锁屏 → 会出现画中画小窗。
       回前台它自动收起。
       画中画上那个播放/暂停按钮没用（下载没法暂停），忽略即可。

出问题时：界面底部会显示画中画起不来的具体原因（不静默失败）。

一个说明：从多任务里上滑「杀掉」App，画中画也会一起没 —— 这是系统边界，
         下一版会用后台传输通道（URLSession 后台会话）补上这一层。

这一版 = 换引擎
────────────────────────────────────────────────────────────

你的实测给出了决定性证据：同一个 .ts，别的转码软件几秒转完
（有声有画面）→ 下载和拼接完全没问题，问题全在我手写的
重封装器上。

所以这版不再自己写 —— 直接内嵌 FFmpeg 引擎（Stay、亚瑟、
各类下载器 App 内部用的同款引擎），转码改用：

    ffmpeg -i 输入.ts -c copy -movflags +faststart 输出.mp4

`-c copy` = 只换容器不重编码：
  · 秒级完成
  · 音轨原样保留（ADTS/B帧/LATM/HEVC 全由 FFmpeg 处理，
    覆盖面比我手写的解析器大几个数量级）
  · +faststart 把索引挪到文件头 → 拖进度条秒响应
  · 完成后自动体检输出文件，过程记录写明：视频轨 ✓/✗、
    音轨 ✓/✗（含采样率声道数）、时长

代价：IPA 从 0.4MB 涨到 9.2MB（FFmpeg 引擎的体积）。
