一、四家对程序的评价（对照）

维度结论
综合定位 Qwen：窄赛道里的极高水平 ｜ MiniMax："个人工具极限流" ｜ MiMo：个人自用工具第一梯队 ｜ DeepSeek：极限流样本，完成度远超普通自用 App
四家共识
最强项		 ① 自研 BSD socket 的本地 HTTP 服务喂 AVPlayer（"别人做不出来、做出来也确实能用"）
② 画中画保活下载（把进度画进 PiP）
③ 几乎零第三方依赖（唯一外援是 FFmpeg 静态库）→ 维护面/崩溃面小
④ 下载自带页面上下文（Referer/UA/Cookie）—— 防盗链站点能下，这是"真工程"
四家共识
最大弱点		 两个 God Object：BrowserModel.swift 121 KB + ContentView.swift 109 KB，撑起近 60% 代码量。 4/4 家都提到（"改一处动全身""状态机是隐式的、汇聚在主线程"）
结构性风险
（各家角度不同）		 · MiniMax（我认为最准）："核心价值寄生在别人的花园里" —— 整个 App 建立在 WKWebView + 第三方网页之上， 站点任何一次升级（HLS 签名、Referer 校验、TS→fMP4、Service Worker 拦请求）都会让某一类资源集体失效，且无后端可兜底， 只能追着改 sniffer.js。
· MiMo："任务生命周期绑定网页会话" —— 嗅探结果、Cookie/Referer、下载入口全锚在活跃标签上， 页面导航 / 标签回收 / JS 上下文重建都会把这条链掐断 → "偶发闪退未定位是这个形态的必然产物，不是运气"。
· DeepSeek / Qwen：下载、嗅探、标签、播放共享生命周期；数据落盘靠 JSON + 人脑。

二、核实成立的建议（附源码证据）

P0-A Cookie 没有随下载任务落盘 —— 本期最实在的一条

谁提的：MiMo（"任务落盘 Cookie/Referer/UA 快照"）
核实：部分成立，且比它说的更具体。 JobStore.swift:147-174 的 JobRecord 落了 referrer、ua，但没有 cookie 字段； Cookie 只在任务运行时从 WebKit 仓现取。
后果：任务暂停/失败后隔夜再续传（或 App 重启后恢复任务），Cookie 已经丢了 —— 防盗链站点会 403/404， 而界面只会说"下载失败"，用户不知道为什么。
改法（小）：JobRecord 加一个可选的 cookie 字段（建卡时快照一次），续传时用它； 失败时提示"登录态可能过期，去页面刷新一下再续"。
要注意：Cookie 里有敏感值 —— 别写进可以被分享出去的「过程记录」。

P0-B 持久化缺 schemaVersion

谁提的：MiMo、DeepSeek（"126 个版本后老数据字段已经不可考"）
核实：成立 —— 全项目搜不到 schemaVersion / 数据版本字段（Bookmarks.json / records.json / tabs.json / watch.json / shortcuts.json 五个落盘文件都没有版本号）。
为什么现在就要：加字段时靠 Codable 的可选值兜底，一旦要"改一个已有字段的含义"（比如 kind 从两态变三态）， 老数据会静默解析错。加版本号是十行的事，等到需要迁移时是几百行 + 一次数据可能丢。

P1-C 嗅探被截断是静默的

谁提的：MiMo（"条目静默截断改为可见"）
核实：成立。两处上限：sniffer.js:398 / 413 各 slice(0, 60)（视频 60 / 图片 60）， 原生侧 BrowserTab.swift:132 maxSniffItems = 300；
但界面上没有任何"已到上限 / 已截断"的说明（只在 Toolbox 副标题里显示条数）。
后果：用户以为"这个站没有更多了"，其实是抓了没显示 —— 对"抓取类工具"是信任问题。
改法（很小）：嗅探面板顶部加一句「共 N 条 · 已达上限，可能有更多」，或按 URL 归并后显示"已合并 X 条"。

P1-D 「过程记录」有数据、但没闭环

谁提的：MiniMax（"埋了等于白埋"）、MiMo（"升级为性能回归基准"）
核实：成立。每个任务记了阶段耗时/内存峰值/主线程最长失联（DownloadJob.notes）， 但只作为单任务存档，没有跨任务基线比对、也没有可视化。
改法（1 天，纯加工既有数据）：任务完成时和历史中位数比，偏差超阈值在诊断页标红； 下载列表条目右侧一条细色条（绿/黄/红）。这是这个 App 最有壁垒的能力，闭环了才值钱。

P1-E 本地 HTTP 服务没有请求日志

谁提的：Qwen
核实：成立（LocalHTTPServer.swift 里没有请求级日志）。 后果：播放黑屏/卡住时无法判断是"服务没收到请求""发了但 AVPlayer 没解析"还是"数据本身坏"。
改法（小）：加一个默认关闭的开关，记录 path / Range / 响应字节数 / send() 的 errno。 （AVPlayer 单路播放，QPS 极低，开销可忽略。）

P2-F 拆 God Object（4/4 家都提，但要权衡）

核实：事实成立，但代价被 AI 低估。BrowserModel 121 KB / ContentView 109 KB 是真的； 四家都建议拆成 SnifferStore / DownloadStore / TabStore / MediaStore。MiniMax 自己给的估算是"纯重构 2-3 周，中途易引入回归"， Qwen 给的是"重构量大"。
我的意见：不建议为了"架构好看"去拆。这是个单机自用 App，没有团队协作、没有 KPI； 盲目大重构会在你最依赖它的时候引入回归。
但有一条值得做：下次改动哪个模块，就顺手把那块的逻辑抽出去（增量式，一次一个）， 不要专门开一个"重构版本"。这也符合他写的「决策梯子」。

四、功能补充建议（27 条 → 去重后 18 条候选）

现状列是我核实过的（不是猜）。"我的推荐"是按这个 App 的形态和他一贯的取舍给的。
功能谁提的现状我的推荐为什么（用户什么时候会用到）
下载列表多选 + 批量
（批量删/批量存相册/批量导出）		 4 家都提没有强烈推荐 一次下了二三十个视频，想清理只能逐个左滑；想批量存相册也做不到。4 家独立命中同一条 = 真痛点。
播放器倍速 + 双击跳转MiniMax、MiMo没有强烈推荐 教程/课程类视频要 0.5x/1.5x、双击左右半屏跳 10 秒。AVPlayer 自带 rate，成本极低，而播放器已经做得很完整了，就差这一块。
播放队列 / 连播Qwen、MiMo、DeepSeek没有推荐 下剧集/分 P 内容，播完一集要手动点下一集。最小版：同一下载批次按文件名排序成队列，播完自动下一个（复用现有"续看"）。
嗅探结果"下载前预览"Qwen没有推荐 嗅探出来一堆地址，用户不知道哪条是正片、哪条是广告。点一下能看前 5 秒就够判断 —— 避免下错资源、白等半天。
按域名的下载后自动动作
（自动存相册 / 自动转 MP4 后删 TS）		 Qwen、MiMo没有推荐 现在下完都停在下载列表，用户再手动点"存相册"。按站配规则（A 站存相册、B 站只留文件）能省掉重复操作。最小版：全局三个开关，默认全关。
"这条已经下过"标记MiMo、DeepSeek没有推荐 换个清晰度重下、或者忘了下过 → 重复占空间。最小版：嗅探条目按规范化 URL 比对本地库，打一个"库里已有"角标，点了直接播。
音频提取（导出 m4a/mp3）DeepSeek没有推荐 只要声音不要画面（课程、播客）。FFmpeg 已经在包里，-vn -c copy 一行事，成本极低。
外挂字幕（.srt/.vtt）DeepSeek没有看情况 下外语视频/学语言时刚需。但代价中等（要接 AVPlayerItem.legibleMedia 那套，还要处理同名自动匹配）。
嗅探规则自定义
（正则过滤 / 域名白名单 / 屏蔽某站）		 Qwen、MiniMax没有看情况 图站一次加载上百资源，真正想下的被挤掉。最小版：设置里一个正则过滤框 + "屏蔽此域名"。
下载前磁盘空间预检MiMo没有看情况 HLS 全程要同时持有原始 TS 和 remux 后的 MP4（峰值约 2× 成品），低空间时下到 90% 失败最伤。但他 C 盘一直紧张的是电脑，手机空间情况我不清楚。
数据备份/恢复
（导出一个 JSON）		MiMo没有看情况 重装 IPA、换机、误删书签 = 全丢。书签已经有 HTML 导出，其余（下载记录/首页/续看）没有。
剪贴板链接入站
（从别的 App 复制链接，切回来直接问"要下吗"）		 MiMo、DeepSeek只有"复制出去"看情况 刷到链接时人在别的 App，切回来还要手动粘贴。最小版：回前台检查剪贴板，弹一次"新标签 / 直接下"。
本地媒体库索引 + 搜索DeepSeek没有看情况 积累几百个文件后找不到。最小版：按文件名/来源域名/日期搜索。
整页归档（把网页本身存下来）MiniMax部分有看情况 下视频时想连教程页一起留。但「导出 PDF」已经覆盖了大半，除非他要"连图片 CSS 一起原样存"。
边下边播DeepSeek没有谨慎 想立刻看不用等。但要动下载主链路（已下载分片生成本地临时 m3u8），与断点续传/取消耦合 —— 风险大于收益。
局域网共享二维码 + tokenMiniMax地址已固定看情况 扫二维码省得输 IP。但地址已经是固定的 18080，收益有限；token 那条是安全项（他还没答"只自用还是要给别人"）。
跨源合并加速
（同一视频多条 CDN，选最快的 / 各取一半）		MiniMax没有谨慎 理论上快 3 倍。但"各取一半"要协调 Range，复杂度高、失败模式多；"选最快"那半可以做。
批量重命名模板MiniMax没有看情况 嗅探下来的文件名多是 hash，没法看。最小版：多选 → 套模板 {标题}-{日期}-{序号}。

五、我的结论

四家的评价我基本认同，但有一点要给他们纠偏：
它们把这个 App 夸得很高（"高水平/第一梯队/极限流"），这是因为它确实把几个别人做不出来的坑啃下来了（本地 HTTP 喂 AVPlayer、 画中画保活、下载带页面上下文）。但 Qwen 和 MiniMax 给的"拆 God Object"方案，代价被它们自己低估了（MiniMax 自己写"2-3 周、易回归"）—— 对一个单机自用工具，为了架构整洁去做 2-3 周的纯重构，风险大于收益。要拆，就"改到哪块顺手拆哪块"。

如果只做 3 条，我选：
① Cookie 随任务落盘（P0-A）—— 十几行，直接消灭一类"不知道为什么就续传失败"；
② 下载列表多选 + 批量（4 家独立命中）—— 他每次下完一批都要逐个处理，这是最日常的摩擦；
③ 播放器倍速 + 双击跳转（成本极低、播放器已完备，就差这块）。

再往后顺手带上：schemaVersion（十行、防未来数据迁移踩坑）、嗅探截断提示（几行、治信任问题）。
