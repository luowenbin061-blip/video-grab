二、P0 —— 真硬伤（建议马上修）

P0-1 ｜ 列表记录可能被一次解码失败“清空” 成立

AI 说法：load 解码失败静默返回空数组；save 失败也被静默忽略。

核实：属实，而且后果比它说的更重 —— JobStore.swift:176-180：load() 解码失败直接 return []； JobStore.swift:187-188：save() 两处 try?，失败静默。 链路是：records.json 一旦损坏（或升级后字段不兼容）→ 列表变空 → 之后任何一次 save()（比如新下一个视频）都会用空列表把文件覆盖掉 → 所有任务的标题、文件名对应关系、回收站状态全没（视频文件还在盘上，但列表对不上号了）。

怎么改：① load 失败时先把 records.json 备份成 records_损坏备份.json 再返回空； ② 逐条容错解码（坏一条丢一条，别全丢）；③ save 失败要能“报出来”（哪怕只是列表页顶部一行红字）； ④ 顺手做滚动备份（保留最近 3 份）。

P0-2 ｜ 拼接段出错时不清理，磁盘满时还会静默产出坏文件 成立

AI 说法：拼接循环里 write 不抛错；解密/读盘抛错时句柄不关、残件不删。

核实：属实。Downloader.swift:273 打开句柄 → :292 decodeIfNeeded（会抛） → :294 out.write(payload) 是 FileHandle 的不抛错版本（磁盘满 = 静默少写）→ :305 的 try? out.close() 只有正常走完才执行。中间任何一步抛错，句柄不关、残缺的 .ts 留在盘上。而且拼接完只查了“缺不缺分片”（:306-310）， 没有把 written 和应有字数对一遍 —— 静默少写的坏文件能过校验。

怎么改：① 整段包 do/catch，catch 里 try? out.close() + 删 outputURL 再 throw； ② 循环结束把 written 和清单声明总字数对一遍，对不上按失败处理。

P0-3 ｜ 局域网共享会把 records.json（含每个站的 Cookie）给出去 成立

AI 说法：共享根目录就是 JobStore.dir，records.json 也在里面，能被下载走。

核实：属实。ContentView.swift:205：enableLAN(root: JobStore.dir)； 服务的防目录穿越只挡“跑出 root”，不挡 root 里面的任何文件。而 records.json 里存着每个任务的 sourceURL / referrer / cookie / UA（防登录态）。同一 Wi-Fi 的人拿到口令（口令本身走明文 HTTP） 就能把这份文件拖走。

怎么改：共享改用白名单虚拟目录：只列“成品视频 + 缩略图”，把 records.json、 parts_*、durations.txt、merge_*.txt 全排除；顺手把口令改成“每次开启随机、关掉即失效” （现在有「记住口令」开关，长期不变就是风险）。

P0-4 ｜ 合并和压缩能同时跑，内嵌 ffmpeg 会被踩崩 成立

AI 说法：两个队列各自独立，可能同时进 ffmpeg；Hook.m 的 jmp_buf 是全局的，线程安全未知。

核实：属实。Hook.m:17 static jmp_buf j; 是全局唯一， FFmpeg_exit 一律 longjmp 到“最后一次 setjmp”的点；而 MergeQueue 和 CompressQueue 是两个互不知晓的独立队列 —— 你一边压画质一边合并视频，两条路同时进 FFmpeg_main， 全局状态（nb_input_files 等）互踩 → 轻则输出错乱，重则直接崩。

怎么改：最省事：所有 HookFFmpeg 调用套同一把串行锁（NSLock 即可）； 或者干脆把两个队列并成一个（都吃 ffmpeg，本来就该排队）。另外 ffmpeg 的调用点建议加 “同一时间只允许一个”的断言，谁违规谁打日志。

三、P1 / P2 —— 隐性问题

级别结论问题（已核实）证据与改法
P1成立 合并的音频滤镜只 aresample=48000，不统一声道布局； 遇到“有源没音轨”整条退回 concat demuxer + -c copy —— 那正是当年“时长暴涨 3.86 倍”淘汰掉的老路 Merger.swift:425（只有 aresample）、:383（allHaveAudio==false 走 demuxer）。 改：音频滤镜加 aformat=sample_rates=48000:channel_layouts=stereo； 无音轨的源补 anullsrc 静音轨
P1成立 合并/压缩两条队列之外没有任何 ffmpeg 串行保护（P0-4 的根因，单列一条因为修法独立） 全项目 grep 不到 NSLock/Semaphore；Hook.m:17 全局 jmp_buf
P1成立 分片下载的 catch 不区分“取消”：点暂停/取消后还会把重试次数耗完（try? Task.sleep 也吞取消） Downloader.swift:474-497。改：catch 里先判 Task.isCancelled 直接 throw； 重试前 try Task.checkCancellation()
P1成立 共享走 0.0.0.0 + 明文 HTTP + 口令（公共 Wi-Fi 可嗅探） LocalHTTPServer.swift:91。属已知取舍：建议共享页加一句“只在信任的网络开” + 口令一次性化
P2成立 snapshot() 里 finishedAt = finished ? Date() : nil —— 完成后每次存档都刷新完成时间 （目前只影响共享页的排序显示） DownloadJob.swift:301 附近；唯一用途 LocalHTTPServer.swift:719。 改：加存储属性，完成那一刻设一次
P2成立 pause/cancel 后 task = nil 不等旧 run 退出，快速“暂停→继续”可能新旧两个 run 短暂并存 （分片写入是 .atomic，兜住了大头） DownloadJob.swift:318-346。改：run 挂代次号（generation），旧任务没退干净就不开新的
P2部分成立 分片下载整段进内存（URLSession.data(for:)）——默认并发 6，普通分片（0.5~3MB）峰值约 18MB， 没事；遇到超大分片（20MB+）才会顶内存 Downloader.swift:466 + :39 concurrency = 6。 改：换 bytes(for:) 流式落盘
P2部分成立 localPlaybackURL() 的 HLS 回退分支判的是 outputName 存在与否 —— 正常流程 outputName 都有值，只有异常态才误判 DownloadJob.swift:358-370。改：回退分支判 playlistName 并放行 outputName 为空的情况

四、推翻的 3 条（代码里有那段，但走不到）

AI 说的核实结果
推翻 “CompressQueue 对外部文件先 moveItem，会把原文件搬走” —— 代码属实 （CompressQueue.swift:251-267，先搬、搬不动才拷），但全项目只有一个调用方 （ContentView.swift:2121），传的是 JobStore.file(named:) —— 永远在自家目录里，inOurDir == true，搬的那条分支当前不可达。 ★ 记下来：以后若支持“从文件 App 直接选片压缩”，这里就是坑，要改成只拷贝。
推翻 “Merger.merge 始终走 concatCopy，force 之后也不改走重编码，参数不一致会产出坏文件” —— 代码属实（Merger.swift:249-255），但 Merger.merge 没有任何调用方： 实际链路是 MergeSheet → inspect（确认弹窗）→ MergeQueue → mergeByReencoding。 所以“硬拼坏文件”不会发生。顺带的真实问题是反的：零损失的 concatCopy 现在没人用 （同规格也重编码）—— 这是你为画质做的已知取舍，要不要把“完全同规格就走 copy”接回队列，你定。
推翻 “inspect 不看帧率，帧率不同也硬拼” —— Merger.swift:215-221： allSame 的判据 = 尺寸 + SPS/PPS 字节指纹 + 帧率，fps 在里面。它说的 warnings 只列尺寸/声道 属实，但 warnings 只影响提示文案，不影响路径选择。

五、缺什么功能（DeepSeek 没给这段，以下是我按“单人自用追剧”场景补的）

建议为什么值得代价
失败自动重试（带次数与间隔上限，界面上能看到“第 N 次”） 追剧最烦的是半夜下一半失败；现在只有嗅探失败有一次自动重试（autoRetried），下载失败要手点 小。状态机已有暂停/继续，套一层就行
records.json 自动备份（保留最近 3 份） 配合 P0-1，这是“列表全没”的最后一道保险 极小，十几行
连播（列表里点播完一集自动播下一集，可关） 追剧场景的高频动作；播放器已有“上次看到哪”的续看 中。要在 PlayerSheet 加“播完回调 + 下一集选择”
共享口令一次性化（默认随机、关闭即失效） 配合 P0-3，把“长期口令”这个风险去掉 小。已有「记住口令」开关，把默认反过来即可
没列的：字幕、多用户、云同步、界面换肤 —— 要么站点不给数据，要么不是自用刚需，先不碰。

六、如果只改三处

1. JobStore.load/save 健壮化（P0-1）—— 一次解码失败就能把列表清空，这是全项目唯一 “用户会觉得东西全没了”的路径，而且修法只有十几行。

2. 共享改白名单目录（P0-3）—— records.json 里有你的登录态，这是唯一会“泄出去”的点。

3. HookFFmpeg 套全局串行锁（P0-4）—— 一把锁堵住“合并+压缩同跑就崩”的整类问题。

第四顺位：Downloader 拼接段的清理（P0-2），改法机械，风险低。以上都等你点头再动手。
